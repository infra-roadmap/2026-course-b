コースB：OCI限定コース（AWS資格を目指さない）

ここまで学んだ知識を組み合わせ、実務に近い3層アーキテクチャを構築します。OCIの正解手順を先に見るのではなく、要件だけを読んで自分で設計し、あとからOCIのベストプラクティスと比較して直す、という実務に近い順序で進めます。AWS資格は目指さないため、その分OCI IAMポリシーを深掘りします。

💼 この月で実務的にできるようになること：与えられた要件からPublic Subnet／Private Application Subnet／Private Database Subnetの3層構成を自分で設計し、設計理由を説明した上でTerraformコードとして構築できるようになります。あわせて動的グループ（Dynamic Group）や条件付きポリシーを使った実務レベルのOCI IAM設計、意図的な障害からの切り分け・復旧、変更をbranchで管理する流れも身につけます。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
3層アーキテクチャPublic Subnet／Private Application Subnet／Private Database Subnetの3層に分ける設計外部公開する層（Public）、アプリが動く層（Private Application）、データを守る層（Private Database）を分離するのが定石。「DB層のCompute」ではなく「Database用途を想定したPrivate Subnet上のCompute」という理解で扱う
動的グループ（Dynamic Group）Compute等のリソースをグループとして扱う仕組み「特定のタグが付いたインスタンス」のようにルールでグループ分けし、そのグループにPolicyで権限を与えられる
条件付きポリシー特定の条件下でのみ有効なポリシーwhere句を使って「特定のコンパートメントに対してのみ」のように絞り込める

WEEK 01目安 4h

要件から考える3層アーキテクチャ設計

🎯 このタスクのゴール
OCIの正解構成を先に見るのではなく、要件だけを読んで自分で設計し、そのあとでOCIのベストプラクティスと比較して必要なら直す、という順序で3層構成（Public Subnet／Private Application Subnet／Private Database Subnet）を設計する。12月までに構築済みのPublic/Private 2層構成（VCN・Subnet・Compute）はそのまま活かし、Private SubnetをDatabase用途として整理したうえで、新たにPrivate Application Subnetを設計に加える形にする。ゼロから作り直すわけではない。なお、10月にPrivate Subnet内に作成したCompute（10月Week4の任意演習で作成したもの）は、存在する場合のみDatabase用途のComputeとしてそのまま引き継ぐ。10月Week4の任意演習を実施しておらず該当Computeが存在しない場合は、このComputeを前提とせずに設計を進めてよい。なお、Private Database Subnetに配置するのは実際のデータベース製品ではなく、Database層を想定したCompute（サーバー）である。
📋 与えられる要件（このまま自分で設計する）
  • WebサーバーはInternetからアクセス可能であること
  • ApplicationサーバーはInternetから直接アクセス不可であること
  • DatabaseサーバーはInternetから直接アクセス不可であること
  • ApplicationからDatabaseへの必要な通信のみ許可すること
  • Private SubnetからOSアップデートなど外部への通信は可能にすること
  • 管理者はBastion経由でPrivate側へSSHできること（Bastion自体はPublic Subnetに置き、Private側への唯一のSSH入口として機能させる。Private Subnet宛のSSH（22番）はBastionからのみ許可し、Internet全体には公開しない）
  • SSHをInternet全体には公開しないこと
📚 使う教材
  • OCI公式ドキュメント（Networking（ネットワーキング）／Architecture Center）※手順3で、自分の設計と比較する際に使う https://docs.oracle.com/ja-jp/iaas/Content/Network/Concepts/overview.htm
🛠 具体的な手順
  1. OCIのドキュメントを見る前に、まず自分で設計する。上記の要件を満たすため、Subnet（Public／Private Application／Private Database）・Route Table・Internet Gateway・NAT Gateway・NSG・Bastion・IAMをどう配置するかを自分で考える。12月時点の構成（VCN├Public Subnet└Compute、Private Subnetは10月作成のComputeが存在する場合はそれを1台含む）を土台にし、Private Application Subnetを新設して3層へ拡張する形で考えるとよい。
  2. 設計した構成図をdraw.ioまたは手書きで作成する。あわせて「なぜPublic Subnetにするのか」「なぜPrivate Application/Private Databaseを分けるのか」「なぜNAT Gatewayが必要なのか」「なぜそのNSGルールなのか」を、この時点の自分の理解で一度言葉にしてメモする。
  3. OCI公式ドキュメントで答え合わせをする。推奨されるネットワーク分離パターンを確認し、自分の設計と見比べる。異なる点があれば、なぜOCI側がそうしているのかを考え、必要に応じて設計図を修正する。一致していた部分もそのまま残してよい。
  4. 修正後の最終構成図を完成させる（Private Subnet内の既存Computeは「Database用途を想定したPrivate Subnet上のCompute」として位置づける）。
✅ 成果物
💡 設計理由メモの書き方（フォーマット例）

内容そのものではなく、書き方の型の例です（正解の構成図はここには書きません。まず自分で考えてください）：

（要件のうち、どれを満たすためにこう配置したか）

■ なぜPrivate Application SubnetとPrivate Database Subnetを分けたか
（分けなかった場合と比べて何が変わるか）

■ なぜそのNSGルールにしたか
（許可した通信・拒否した通信とその理由）

🧭 到達判定

  • OCI公式の推奨パターンと自分の設計を比較し、違いがあればその理由を説明できる

WEEK 03目安 3.5h

Compute構築（Application層の追加［全員必須］とDB想定Computeのimport［存在する場合のみ］）

🎯 このタスクのゴール
新設したPrivate Application SubnetにComputeをTerraformで構築し、踏み台構成の役割分担を整理することを、全員の必須到達点とする。あわせて、10月に手動作成したPrivate SubnetのDatabase用途Computeが存在する場合は、それをこれまでに書いたTerraformコードで管理できる状態にする（存在しない場合はこの部分の演習は不要）。
📚 使う教材
  • Terraform公式ドキュメント（terraform importのページ） https://developer.hashicorp.com/terraform/cli/import
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う（引き続きWEEK02のfeature/three-tier-design branch上で作業する）。
  2. （条件付き演習：10月Week4の任意演習を実施済みで、対象のPrivate SubnetのComputeが存在する場合のみ実施する。存在しない場合は手順2〜4を飛ばして手順5へ進む。） 10月に手動作成したPrivate SubnetのCompute（VM.Standard.E2.1.Micro、Database用途）に対応するoci_core_instanceリソースブロックをTerraformコードに書く（display_nameやshapeなど、既存インスタンスの設定値をOCIコンソールで確認しながら合わせる）。
  3. terraform importで、書いたリソースブロックと実際のインスタンスを紐付ける（手動作成した既存リソースをTerraform管理下に置く操作）。実行するコマンドは次の形。
    terraform import oci_core_instance.db_instance ocid1.instance.oc1...（対象インスタンスのOCID）
    oci_core_instance.db_instanceの部分は手順2で書いたリソースブロックの"oci_core_instance" "db_instance"に、OCIDはOCIコンソールのインスタンス詳細画面からコピーする。
  4. terraform planを実行し、差分が出ないこと（＝コードと実物が一致していること）を確認する。差分が出た場合は、コード側の設定値（Shapeやサブネット等）が実際のインスタンスと食い違っているので、表示された差分を1つずつ実際の値に合わせて書き直す。
  5. Private Application SubnetにComputeを新規構築する（全員必須）。 ただし、10月Week4のPrivate Computeが存在する場合は、新規作成前に整理すること。Public用・10月Private用・今回のApplication用でE2.1.Microが3台となり、Always Free上限（E2.1.Micro最大2台）を超える可能性があるため、不要な10月Week4のPrivate Computeは、手順2〜4でTerraform管理下に置いたoci_core_instance.db_instanceをTerraformコードとstateの両方から削除する（コードのresourceブロックを削除したうえでterraform planで削除対象を確認し、terraform applyで実体を削除する。OCIコンソールから直接削除すると、コード・stateには存在したままになり不整合が生じるため行わない）か、Always Free枠内に収まる別の構成に変更してから進める。10月Week4を実施しておらず該当Computeが存在しない場合は、従来どおりそのままApplication Computeを新規作成してよい。整理が完了したら、WEEK02で作成したPrivate Application Subnetにoci_core_instanceリソースを新たに追加し（ShapeはVM.Standard.E2.1.Micro）、terraform applyで構築する。既存のDB想定Computeとは別インスタンスであることを確認する。
  6. Public Subnet側のインスタンスを踏み台（Bastion）とし、Private側へのアクセス経路を整理する。基本はssh -JによるProxyJumpを使う（Bastionに秘密鍵を置かずに済み、踏み台経由の接続先を1コマンドで指定できるため）。
    ssh -i .\ダウンロードした鍵ファイル.key -J ubuntu@Public側のIP ubuntu@Private側のIP
    参考として-Aオプション（エージェント転送）で2段階SSHする方法も試してよいが、こちらはBastion上のプロセスに自分の鍵の代理利用を許可する方式のため、Bastionが乗っ取られた場合のリスクがProxyJumpより大きい点に注意する。
⚠️ つまずきやすいポイント
  • 10月Week4の任意演習（NAT Gateway発展演習）を実施していない場合、import対象となる10月作成のPrivate SubnetのComputeが存在しない。その場合は、このimport演習はスキップして次の演習（Private Application SubnetへのCompute構築）へ進んでよい。新たにComputeを用意する必要はない。

WEEK 04目安 4h

OCI IAM設計＆障害切り分け演習、branch push

🎯 このタスクのゴール
9月に作った基本のIAM知識を発展させ、「要件→必要な権限→Policy」の順で考える実務的なIAM設計を体験する。あわせて、今月構築した3層構成に対して意図的な障害を起こし、自力で切り分けて復旧する総合演習を行う。
📚 使う教材
  • OCI公式ドキュメント（Dynamic Groups（グループ）／Policy Reference） https://docs.oracle.com/ja-jp/iaas/Content/Identity/Tasks/managingdynamicgroups.htm
🛠 具体的な手順（IAM設計）
  1. 要件から必要な権限を考える。「Compute Instanceがオブジェクト・ストレージのapp-logsバケットにログを書き込めるようにしたいが、それ以外の操作はできないようにしたい」という要件を例に、まず「その要件を満たすために最低限必要な権限は何か」を先に自分の言葉で書き出す。いきなりPolicy文を書き始めない。
  2. 動的グループ（Dynamic Group）の概念を学び、Compute（コンピュート） InstanceをPrincipalとして扱うための条件式を、洗い出した要件に沿って作成する。
  3. 条件付きポリシー（where句）を使い、手順1で洗い出した権限だけに絞ったPolicyを作成する（「全リソースに対するmanage権限」のような広すぎる権限にしない）。
  4. 設計内容（要件→必要な権限→Policy文の順）をMarkdownでドキュメント化し、study-notesリポジトリに2027-01-oci-iam-design.mdとして保存してpushする。
🧪 総合トラブルシュート演習
「Private Application SubnetのComputeから、Private Database SubnetのComputeへのTCP疎通（SSH＝22番ポートを使って確認）ができない」状態を意図的に作り、原因を自分で切り分けて復旧する。この演習で扱うのはあくまでPrivate Compute間のTCP疎通障害であり、DB（データベース）サービスそのものの障害ではない点に注意する（Database Subnet側のComputeは、DBサービスの稼働有無に関わらず、疎通確認の対象ホストとして扱う）。9〜12月のSSH／NAT Gatewayの演習とは別に、今月構築した3層構成そのものを対象にする。
  1. 正常な状態を確認しておく。 Bastion経由でPrivate Application SubnetのComputeに接続し、そこからPrivate Database SubnetのCompute宛に疎通確認（例：nc -zv <DB側のプライベートIP> 22）が通ることを確認しておく。
  2. 障害を発生させる(次の①②を、この順番で実施する)。 ①まずNetwork/NSGレベルの障害を作る。 Private Database Subnet用のNSGのIngressルールから、Application Subnet側CIDR（またはApplication用NSG）を許可する行を削除する。同じ疎通確認コマンド（nc -zv <DB側のプライベートIP> 22）を再実行して失敗を確認したら、ルールを元に戻して復旧することを確認する。②次にOS側（Serviceレベル）の障害を作る。 NSGは正常な状態のまま、Database Subnet側ComputeにSSHで接続し、sudo systemctl stop sshを実行してSSHサービスそのものを停止する（すでに接続しているSSHセッションは保持したまま行う）。これは「OS Firewall（ufw等、通信の許可・拒否を制御する層）」ではなく「Service（サービスプロセス自体が起動しているかどうか）」の障害を再現するものである点に注意する。仮にOS Firewallの障害を再現したい場合は、sudo ufw deny 22/tcpのようにポート単位で拒否するのが対応する操作になるが、本演習ではService層（systemctl stop ssh）のみを扱う。同じ疎通確認コマンドを再実行し、NSGは正常なのにSSHサービス停止によって失敗することを確認する。
  3. 症状を確認する。 ①②それぞれについて、疎通確認コマンドが失敗することを確認する。
  4. どの順番で確認したかを記録しながら切り分ける。 「Client → Network(Route Table) → NSG → OS Firewall → Service」という切り分けの考え方に沿って、ip route・OCIコンソールのNSG設定確認・OS側のsudo ufw status（OS Firewall層の確認。本演習では正常のはず）・systemctl status ssh（Service層の確認）などを、確認した順番どおりに書き出す（「①まずNSGを疑って確認したが正常だった→②次にOS Firewall（ufw）を確認し、これも正常だった→③最後にServiceの状態（systemctl status ssh）を確認し、SSHサービスが停止していることが原因だと特定した」という形式）。同じ「通信できない」という症状でも、原因の階層（NSGか、OS Firewallか、Serviceか）によって確認すべき箇所が異なることを体験する。
  5. 原因を特定し、復旧する。 ①のNSGルールを、削除する前の状態（Application Subnet側CIDRまたはApplication用NSGを許可するIngressルール）に戻す。②のOS側は、保持しておいたSSHセッションから
    sudo systemctl start ssh
    を実行してSSHサービスを起動し直す。続けて
    sudo systemctl status ssh
    を実行し、active (running)と表示されることを確認する（ufwを止めていた場合は同様にsudo ufw enable等で元の状態に戻す）。最後に、Bastion経由のApplication側Computeから同じ疎通確認コマンド（nc -zv <DB側のプライベートIP> 22）を再実行し、①②のどちらも復旧して疎通が通ることを確認する。
  6. 「①発生させた障害の種類 ②確認した順番と分かったこと ③原因 ④復旧方法」を3〜5行程度でまとめ、study-notesリポジトリに2027-01-troubleshoot.mdとして保存し、pushする。

OCI IAM設計ドキュメントの構成例（study-notesリポジトリの2027-01-oci-iam-design.mdとして保存するイメージ）：

## 要件
- Compute InstanceがOCI Object Storageのapp-logsバケットに書き込みできるようにする
- それ以外の操作は許可しない

## 必要な権限（要件から洗い出し）
- 「書き込み（オブジェクトの作成）」ができれば要件を満たす。読み取り・削除・一覧参照などは今回の要件には含まれないため付与しない
- OCIのObject Storage Policy verbは4段階（inspect < read < use < manage）で、「作成」はreadより強い権限が必要なため、readでは要件を満たせない点に注意する
- manage object-familyを丸ごと許可すると削除等も可能になり過剰なため、objectリソース種別＋permission指定で絞り込む

## 動的グループ設計
- グループ名: compute-dyn-group
- 条件: instance.compartment.id = 'ocid1.compartment...'

## 条件付きポリシー例
Allow dynamic-group compute-dyn-group to manage objects
  in compartment dev where all {target.bucket.name = 'app-logs',
  request.permission = 'OBJECT_CREATE'}

## 設計方針
- 「全リソースに対するmanage権限」は使わず、必要なリソース種別・permissionだけに絞る
- 「manage object-family」のような広い許可ではなく、対象バケットとrequest.permissionで書き込み用途だけに限定する
- 本番/開発でコンパートメントを分離し、ポリシーもコンパートメント単位で管理する
🧭 到達判定
  • 「要件→必要な権限→Policy」の順でIAM設計を進められる
  • 動的グループと条件付きポリシーの役割を説明できる
  • Network／NSG／OS Firewall／Serviceの階層に沿って通信障害を切り分け、復旧できる
