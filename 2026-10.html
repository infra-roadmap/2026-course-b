学習ロードマップ（詳細版）

10月：OCIネットワーク

コースB：OCI限定コース（AWS資格を目指さない）

ネットワークの基礎（CIDR、Subnet、NSG、ルーティング）を学び、実際にインターネットへ出られるネットワークを構築します。AWS資格は目指さないため、その分OCI側の理解を深めます。

💼 この月で実務的にできるようになること：CIDR設計をもとにVCN・Public/Private Subnet・NSG・Route Tableまでを、Always Free枠の範囲内で設計から構築まで担当できるようになります。あわせて、Private SubnetからのアウトバウンドをNAT Gateway経由で許可する構成についても理解します（NAT GatewayはAlways Free対象外のため、実機構築は任意・課金注意の発展演習として扱います）。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
CIDRネットワークの「番地」の表し方例：10.0.0.0/16。「/16」の数字が大きいほど範囲が狭くなる
パブリック／プライベートSubnetVNICにパブリックIPを割り当てられる区画／割り当てない区画Subnetは作成時にPublic SubnetまたはPrivate Subnetとして指定する。Public SubnetではVNICにパブリックIPを割り当てることができ、Private SubnetではVNICにパブリックIPを割り当てない（インターネットから直接アクセスさせない用途で使う）。Route Tableは「Subnetからどこへ通信を転送するか」を定義するものであり、Public/Privateの区分そのものを決めるものではない点に注意（Internet GatewayやNAT Gatewayへの経路をRoute Tableで設定する）
NSG（Network Security Group）VNICに適用する通信の許可ルールVNICに適用して「どのポート番号を」「どこからのアクセスに対して」開けるかを制御する仕組み。同様の制御はSecurity Listでも可能で、NSGは必須ではないが、本ロードマップではNSGを使って学習する。外部と通信できるかどうかは、NSGだけでなくSubnet・Route Table・Internet Gateway等のネットワーク構成とセキュリティルール全体によって決まる
ルートテーブル通信の行き先を決める地図「このIP範囲宛の通信はここへ送る」というルールの一覧
インターネットゲートウェイVCNとインターネットの出入口Public SubnetからInternet Gateway経由でインターネットと直接通信するために、Route Tableにこれへの経路を設定する。NAT GatewayやService Gatewayなど、目的に応じた別の出口もある
NATゲートウェイPrivate Subnetから「出るだけ」を許可する仕組み外からは中に入れないが、中から外へは通信できる。ソフトウェア更新等に使う。Always Free対象外で、稼働時間や処理データ量に応じて課金されるため、このロードマップでは実機構築を任意・課金注意の発展演習として扱う

WEEK 01目安 3h

CIDR設計の基礎、VCN作成

🎯 このタスクのゴール
ネットワークの「番地」の考え方（CIDR）を理解する。あわせて、9月に作成したVCN・Computeを削除してから、今度は10月用として手動でVCNを1つ作れるようになる（9月→10月→11月を通じてVCNを常に2個以下に保つため、9月分は先に片付けてから10月分を作る）。
📚 使う教材
  • OCI公式ドキュメント（Networking（ネットワーキング） Overview） https://docs.oracle.com/ja-jp/iaas/Content/Network/Concepts/overview.htm
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. 9月に作成したVCN・Computeを削除する。 まず「Compute」→9月Week3で作成したインスタンスを選択し「Terminate（インスタンスの終了）」で削除する。続けて「Virtual Cloud Networks」→9月に作成したVCNを開き、Subnet・Internet Gateway・NAT Gateway・Route Table・Security Listなど内部の依存リソースが残っていれば先に削除したうえで、VCN本体を削除する（依存リソースが残っているとVCNは削除できない）。ここで9月分を片付けておくことで、9月→10月→11月を通じてVCNが常に2個以下に保たれる。
  3. CIDR表記を学ぶ。 例えば10.0.0.0/16の「/16」は先頭16ビットがネットワーク部という意味で、10.0.0.0〜10.0.255.255の約6万5千個のアドレスを含む、という理解でまずはOK。
  4. VCNを手動で作成する。「Virtual Cloud Networks（仮想クラウド・ネットワーク）」→「Create VCN（VCNの作成）」（ウィザードは使わない）で、CIDR 10.0.0.0/16 を指定して作成する。
  5. 作成内容を確認する。 VCNの詳細画面でCIDRブロックが正しく表示されていることを確認する。
  6. CIDR計算を自分の手で練習する。 10.0.0.0/16を4つの/18に分割した場合、それぞれのアドレス範囲がいくつになるかを計算し、正しいか確認する（オンラインのCIDR計算ツールで答え合わせしてOK）。翌週以降のSubnet設計で必ず使う考え方なので、ここで一度手を動かしておく。study-notesリポジトリに2026-10-cidr-practice.mdとして保存する。
⚠️ つまずきやすいポイント
  • CIDRの範囲は後から変更しづらいので、学習用途でも10.0.0.0/16のような広めの範囲を最初に確保しておくと後で困らない。
✅ 成果物
🧭 到達判定
  • CIDR表記が何を意味するか説明できる
  • 10.0.0.0/16を複数の/18に分割したときのアドレス範囲を自分で計算できる
WEEK 02目安 2h

Subnet設計（Public/Private）

🎯 このタスクのゴール
1つのVCNの中に「外部公開用」と「非公開用」の2つの区画を作る。
📚 使う教材
  • OCI公式ドキュメント（Networking（ネットワーキング）） https://docs.oracle.com/ja-jp/iaas/Content/Network/Concepts/overview.htm
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. Public Subnetを作る。「Subnets（サブネット）」→「Create Subnet（サブネットの作成）」。名前public-subnet、CIDR 10.0.1.0/24。
  3. Private Subnetを作る。 名前private-subnet、CIDR 10.0.2.0/24。
  4. Subnet Access設定を確認する。 それぞれの詳細画面で、意図した公開設定になっているか確認する。
  5. Public Subnet用のRoute Tableを作る。「Route Tables（ルート表）」→「Create Route Table（ルート表の作成）」でpublic-route-tableを作成する（この時点ではルールは追加しない）。
  6. Private Subnet用のRoute Tableを作る。 同様にprivate-route-tableを作成する。
  7. 各SubnetにRoute Tableを割り当てる。 public-subnetの詳細画面から「Edit Subnet（サブネットの編集）」を開き、Route Tableをpublic-route-tableに変更する。同様にprivate-subnetにはprivate-route-tableを割り当てる。デフォルトのRoute Tableを両Subnetで共有したままだと、片方に追加したルールがもう片方にも適用されてしまうため、ここで明示的に分離しておく。
⚠️ つまずきやすいポイント
  • この時点ではまだRoute Table（ルート表）にルールを設定していないため、実質どちらも「外に出られない」状態。区別が本当に効いてくるのは第3〜4週。
✅ 成果物
🧭 到達判定
  • Public SubnetとPrivate Subnetの違いを説明できる
  • Public Subnet用とPrivate Subnet用でRoute Tableを分離する理由を説明できる
WEEK 03目安 3.5h

NSG、Route Table

🎯 このタスクのゴール
「誰からのどんな通信を許可するか」のルールを作り、Public Subnetに最低限の穴（SSHのみ）だけを開ける。
📚 使う教材
  • OCI公式ドキュメント（Network Security Groups（ネットワーク・セキュリティ・グループ）） https://docs.oracle.com/ja-jp/iaas/Content/Network/Concepts/networksecuritygroups.htm
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. NSGを作る。「Networking（ネットワーキング）」→「Network Security Groups（ネットワーク・セキュリティ・グループ）」→「Create Network Security Group（NSGの作成）」でpublic-nsgを作成する。
  3. Ingressルールを追加する。 TCP 22番（SSH。可能であれば自宅のグローバルIPからのみ許可）を追加する。自宅のグローバルIPは、ブラウザで「IP確認」と検索するかhttps://www.cman.jp/network/support/go_access.cgiのようなサイトで調べられる。末尾に/32を付けて1つのIPだけを許可する形で入力する（例：203.0.113.5/32）。この時点ではまだ外部公開するWebサーバーを構築していないため、TCP 80番（HTTP）のIngressルールは開けない（最小権限の考え方。Webサーバー公開が必要になった際に、その時点で必要なルールだけを追加する）。
  4. Default Security Listを確認・修正する。 Subnetには、NSGとは別に「Default Security List for <VCN名>」が自動的に紐づいている。ここにSSH（TCP 22番）を0.0.0.0/0で許可するIngressルールが残っていないか確認し、残っていれば削除する（NSG側で自宅IPの/32に制限していても、Security List側に全世界許可が残っていると、そちらの許可でSSHが通ってしまう）。
  5. Route Tableの現状を確認する。 Week2で割り当てたpublic-route-table（public-subnet用）を開き、まだルールが無いことを確認する（次週で追加する。private-route-tableとは別のRoute Tableであることもあわせて確認しておく）。
  6. Public SubnetにComputeを1台作成する。「Compute（コンピュート）」→「Instances（インスタンス）」→「Create Instance（インスタンスの作成）」を開き、Subnetはpublic-subnetを選ぶ（Public IPを自動割り当てにする）。ShapeはVM.Standard.E2.1.Microを選ぶ（Ampere A1のAlways Freeとは別枠になっているAMDベースのシェイプ（最大2台まで無料）も、この10月であわせて体験しておく）。SSH鍵は新規に発行し、その場でPCに保存する。以降、この10月用VCN内のNSG設定・疎通確認はすべてこのComputeを対象に行う。
  7. 作成したNSGを、上記で作成した10月用のComputeインスタンスに実際にアタッチする。 NSGは作成しただけでは何にも効果がなく、対象のVNICに紐づけて初めて機能する。「Compute」→対象インスタンス→「アタッチされたVNIC」→「Network Security Groups（ネットワーク・セキュリティ・グループ）」の編集からpublic-nsgを追加する。
  8. ルールが本当に機能しているかを確認する。 許可していないポート（例：TCP 3389）宛にブラウザやコマンドで接続を試み、つながらないことを確認する。「作成した＝動いている」ではないことを、意図的な失敗で体感しておく。
⚠️ つまずきやすいポイント
  • SSHの22番を0.0.0.0/0（全世界）に開けたままにするのはセキュリティリスクが高い。
  • Security ListとNSGは、どちらか一方で許可されていれば通信可能（ANDではなくOR）。 NSGでSSHを自宅IPに制限しても、Security List側に0.0.0.0/0の許可が残っていると全世界からSSHできてしまうため、両方を確認する必要がある。
  • 自宅のグローバルIPは多くの場合「動的IP」で、時間が経つと変わることがある。数日後に急にSSHで繋がらなくなったら、まずグローバルIPが変わっていないか確認し、変わっていればNSGのIngressルールを新しいIPに更新する。
✅ 成果物
🧭 到達判定
  • NSGは作成しただけでは機能せず、対象のVNICにアタッチして初めて効果を持つことを説明できる
  • 許可していないポートには接続できないことを、実際に確認できる
  • Security ListとNSGの許可がOR条件で評価されることを理解し、意図しない許可が残っていないか確認できる
WEEK 04目安 5.5〜6.5h

Internet Gatewayの設計と構築（＋NAT Gateway：任意・課金注意）

🎯 このタスクのゴール
（必須）Public SubnetのComputeからインターネットへ疎通できる状態を、Always Free枠の範囲内で作る。（任意）余力があれば、下記の発展演習でPrivate SubnetからもNAT Gateway経由でアウトバウンド通信だけができる状態まで作る。
📚 使う教材
  • OCI公式ドキュメント（Internet Gateway／NAT Gateway） https://docs.oracle.com/ja-jp/iaas/Content/Network/Tasks/managingIGs.htm
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. Internet Gatewayを作る。「Internet Gateways（インターネット・ゲートウェイ）」→「Create Internet Gateway（インターネット・ゲートウェイの作成）」し、Public Subnet用のRoute Table（public-route-table）に0.0.0.0/0 → Internet Gatewayを追加する。
  3. 疎通確認する。 Public Subnet上のCompute（コンピュート）から
    curl https://example.com
    を実行し、インターネットに出られることを確認する。
  4. 構成図を作る。 draw.ioでネットワーク詳細構成図（CIDR・NSG・Route Table（ルート表）・Internet Gatewayを含む）を作成し、PNGとして保存する。下記の任意演習でNAT Gatewayも構築した場合は、その内容もあわせて構成図に追記する。
  5. GitHubに保存する。 oci-learning-logリポジトリのREADME.mdに画像を追加し、9月の構成図と合わせて更新してpushする。
⚠️ つまずきやすいポイント
  • NAT GatewayはAlways Free対象外です。 Internet Gatewayとは異なり、稼働時間および処理データ量に応じて課金されるため、このロードマップでは必須演習には含めていません。下記「任意・発展演習」として実施する場合は、課金が発生しうることを理解したうえで進め、確認が終わったらNAT Gatewayを削除するなど、使い終わったリソースの後片付けを忘れないこと。
  • NAT Gatewayは「中から外」の一方通行。「外から中」を許可したい場合はInternet GatewayやBastion構成が必要になる、という違いを意識しておく。
  • 発展課題（任意）：Service Gateway。 Private SubnetからOCI Object StorageやOCI Autonomous Database等、OCI内部のサービスにだけアクセスしたい場合、NAT Gatewayを経由すると一度インターネット側に出てから戻ってくる形になり無駄が多い。Service Gatewayを使うと、OCIのバックボーンネットワーク内だけを通ってOCIサービスにアクセスでき、インターネットを経由しない分セキュリティ的にも望ましい。余力があれば、Route TableにOCI Services宛のルートをService Gateway経由で追加し、NAT Gateway経由との違いを構成図に書き添えておくとよい（必須ではないため、時間がなければ次月以降に回してよい）。
🧩 任意・発展演習：NAT Gatewayの実機構築（Always Free対象外・課金注意）
Private SubnetからもNAT Gateway経由でアウトバウンド通信だけができる状態を作る。この演習は任意です。 NAT GatewayはAlways Free対象外のため、稼働時間および処理データ量に応じて課金される点に注意し、理解したうえで取り組む場合のみ実施すること。コストを避けたい場合は、実機構築はせず、構成図・ルート設計のみで学習してもよい。
  1. NAT Gatewayを作る。「NAT Gateways（NATゲートウェイ）」→「Create NAT Gateway（NATゲートウェイの作成）」で作成し、Private Subnet用のRoute Table（private-route-table）に0.0.0.0/0 → NAT Gatewayを追加する。
  2. Private SubnetにComputeを作る。「Compute（コンピュート）」→「Instances（インスタンス）」→「Create Instance（インスタンスの作成）」を開き、Subnetはprivate-subnetを選ぶ（Public IPは割り当てない）。ShapeはVM.Standard.E2.1.Micro（Ampere Always Free枠とは別に、AMDベースで最大2台まで無料）を選ぶ（Week3で作成したPublic Subnet側のインスタンスと同じ理由で、この10月ではAmpere A1とは別枠のE2.1.Microを使用している）。作成後、curl https://example.comが外部へは通り、外部からPrivate Subnet宛のアクセスはできないことだけ手早く確認する（1月に一連の構成をTerraform化する際にあらためて詳しく検証するため、ここでは簡易確認でよい）。
  3. 構成図・GitHubを更新する。 上記で作成した構成図にNAT Gatewayを追記し、oci-learning-logリポジトリのREADME.mdを更新してpushする。
🧪 トラブルシュート演習：「通信できない、原因を特定せよ」（任意・上記のNAT Gateway演習を実施した場合のみ）
正常に疎通していたPrivate Subnet上のComputeが外部HTTPSへ接続できなくなった状態を想定し、Linuxコマンドとネットワーク設定の両面から原因を切り分けて復旧する。上記の任意演習でNAT Gatewayを構築していない場合は、この演習はスキップしてよい。
  1. 正常な状態を確認しておく。 Private Subnet上のComputeにSSHで接続し（Public Subnet側のComputeを踏み台として、そこからPrivate Subnet側のComputeへ接続する）、
    curl -v https://example.com
    が正常に通ることを確認しておく。
  2. 障害を発生させる。 Private Subnet用のRoute Table（private-route-table）から0.0.0.0/0 → NAT Gatewayのルールを削除する。
  3. 症状を確認する。 同じComputeから再度curl -v https://example.comを実行し、失敗することを確認する。
  4. Linuxコマンドで切り分ける。 以下を順番に実行し、それぞれの結果と気づいたことを書き留める。
    ip addr ip route ss -lntp ping -c 3 8.8.8.8 dig example.com curl -v https://example.com traceroute example.com
    ip addrでComputeのIP設定自体に問題がないか、ip routeでOS側のデフォルトルートがどこを向いているかを確認する（OS側の設定は正常なことが多く、それが分かると「OCI側のRoute TableかNSGを疑う」という判断材料になる）。ping・dig・traceroute（無ければsudo apt install -y traceroute）で、どこまで到達しどこで止まっているかを段階的に確認する。
  5. OCI側の設定を確認する。 Linuxコマンドの結果から当たりを付けたら、OCIコンソールでPrivate SubnetのRoute Table（ルート表）とアタッチされているNSGのEgressルールを見直し、どちらに問題があるかを特定する。
  6. 復旧する。 削除・変更した設定を元に戻し、curl -v https://example.comが再び通ることを確認する。
  7. 確認した順番を記録する。「①何を確認したか→②何が分かったか→③次に何を確認したか→④原因→⑤復旧方法」の順で、5〜8行程度の箇条書きメモを作る。study-notesリポジトリに2026-10-network-troubleshoot.mdとして保存し、pushする。
