11月：Terraform入門

コースB：OCI限定コース（AWS資格を目指さない）

ここからは手作業ではなく、コードでインフラを構築する「Terraform」を学びます。教材はOracle公式の日本語チュートリアルを使用します。

💼 この月で実務的にできるようになること：手作業で作っていたOCIリソースをTerraformコード（HCL）として書き起こし、init／plan／applyの流れとGitでのコード管理を、実務のIaC運用の基本として自分ひとりで回せるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
Terraformインフラをコードで作るツール「IaC（Infrastructure as Code）」の代表的なツールの1つ。手作業をコードに置き換える
HCLTerraformが使う専用の記述言語HashiCorp Configuration Languageの略。JSONに近いが、もう少し人間が書きやすい構文
ProviderTerraformが操作するクラウドの種類を指定する設定「OCIを操作します」という宣言をコードの先頭に書く
plan / apply変更内容の予告 / 実際の適用plan＝「これから何を作る/変えるか」の確認、apply＝実際に実行
state（ステート）Terraformが管理する「現在の状態」の記録実際に作られたリソースの情報がファイルに記録される。壊すと復旧が大変なので取り扱い注意

週次タスク

WEEK 01目安 4h

Terraform概要、環境構築、Provider

🎯 このタスクのゴール
手作業でポチポチ作っていたVCN等を、これから「コード」で再現できるようにするための土台を作る。
📚 使う教材
  • Oracle公式チュートリアル（日本語）「Terraformの設定」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/01-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. Terraformをインストールする。 PowerShellを「管理者として実行」で開き、
    winget install HashiCorp.Terraform
    を実行する（wingetはWindows標準のパッケージ管理ツール）。インストール後、新しいPowerShellを開き直してterraform -versionでバージョンが表示されることを確認する。本コースではTerraform v1.12.0以上を使用する（3月に使用するOCI Native Backendの要件のため）。表示されたバージョンがv1.12.0未満の場合は、HashiCorp公式サイトから最新版を再インストールする。
  3. OCI CLIをインストールする。 OCI CLIのGitHubリリースページ（https://github.com/oracle/oci-cli/releases/latest）からWindows用MSIインストーラーをダウンロードして実行するのが最も簡単。インストール後、新しいPowerShellでoci --versionが表示されることを確認する。
  4. APIキーを発行し、認証情報を設定する。 これは2段階の作業になる。①PowerShellでoci setup configを実行すると、対話形式で質問されながらローカルに秘密鍵・公開鍵のペアが自動生成される（保存場所はデフォルトのままでよい）。②生成された公開鍵の中身をコピーし、OCIコンソール右上のユーザーアイコン→「User Settings（ユーザー設定）」→「API Keys（APIキー）」→「Add API Key（APIキーの追加）」で貼り付けて登録する。この②を忘れると、①だけでは認証が通らない点に注意。
  5. CLIの疎通確認をする。 oci iam compartment list --compartment-id <テナンシーOCID>を実行し、認証設定が正しくできているかをOCI CLIから確認する（コンパートメント一覧がJSON形式で返ってくればOK）。
  6. Providerを記述する。 作業フォルダにprovider.tfを作り、チュートリアルのサンプルをコピーして自分のテナンシーOCID等に書き換える。
⚠️ つまずきやすいポイント
  • 「Terraform」と「OCI CLI」は別物。oci setup configで生成された認証情報ファイル（~/.oci/config）を、Terraform OCI Providerが直接読み込んで利用する（実行のたびにOCI CLIを経由して認証しているわけではない）、という関係を理解しておくと混乱しにくい。
  • oci setup configで鍵を作っただけでは認証は通らない。生成された公開鍵をOCIコンソール側にも登録する、という2段階セットであることを忘れないこと。
✅ 成果物
🧭 到達判定
  • TerraformとOCI CLIの関係を説明できる
  • APIキー発行とOCIコンソール登録が2段階の作業である理由を説明できる
WEEK 02目安 4h

Resource基礎（VCN構築をコード化）

🎯 このタスクのゴール
10月に手動で作ったVCNと同じものを、コードから再現する。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの構築」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/03-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. main.tfにresource "oci_core_vcn" ...ブロックを記述する。
  3. terraform initを実行する（Providerのダウンロード）。
  4. terraform fmtでコードを整形し、terraform validateで文法エラーが無いことを確認する（plan/applyの前に必ず行う習慣にする）。
  5. terraform planで「何が作られるか」の予告を確認する。
  6. terraform applyを実行し、yesと入力して実際にVCNを作成する。
  7. 10月に手動で作ったVCNは、この時点ではまだ削除しない。Public/Private Subnet・Route Table・NSG（public-nsg）・Compute（10月week3作成分）がまだ紐づいており、依存リソースを持つVCNはそのままでは削除できないため、これらを11月week4（Subnet）・12月（Compute）で順次Terraformコードとして移行し終えたあと、まとめて一本化する（9月分のVCN・Computeは10月着手前にすでに削除済みのため、この時点でのVCNは10月の手動VCNとここで作成したTerraform管理VCNの2個であり、上限内に収まっている）。
⚠️ つまずきやすいポイント
  • terraform applyはいきなり実行せず、必ずplanで内容を確認してから実行する癖をつける。
  • OCIのVCNは、内部にSubnetなどの依存リソースが残っている状態では削除できない。依存リソースを先に整理してから最後にVCN本体を削除する、という順序を意識しておく（実際に手動環境を片付けるのは、Subnet・Computeの移行が完了したあと）。
🧪 意図的な設定ミスからの復旧
HCLの文法ミスをわざと入れて、terraformのエラーメッセージを自分で読んで直せるようになる。
  1. 文法ミスを入れる。 main.tfのresource "oci_core_vcn" ...ブロックの閉じカッコ}を1つ削除するなど、文法エラーになる変更を加える。
  2. エラーを確認する。 terraform validateを実行し、表示されるエラーメッセージ（ファイル名・行番号・エラー内容）を読む。
  3. 直す。 エラーメッセージが指す箇所を自分で直し、terraform validateがエラー無しで通ることを確認する。
  4. 別のミスも試す。 今度は属性名を意図的にtypoする（例：cidr_blockをcider_blockにする）。「そのような属性は存在しない」系のエラーメッセージの読み方にも慣れておく。
✅ 成果物
🧭 到達判定
  • terraform validateのエラーメッセージを読んで、自分でコードを修正できる
  • 文法ミスと属性名のtypoで、エラーメッセージの出方が異なることを説明できる
WEEK 03目安 2.5h

Variable、Output

🎯 このタスクのゴール
CIDRやコンパートメントOCIDのような値を、コードの外に切り出して管理できるようにする。
📚 使う教材
  • Oracle公式チュートリアル「変数の宣言」「出力値の照会」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/04-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. ハードコードしていた値をvariables.tfに切り出す。
  3. terraform.tfvarsに実際の値を書く（秘密情報を含むためGitには入れない）。
  4. outputs.tfにVCNのOCIDを出力する設定を書き、terraform apply後に値が表示されることを確認する。
  5. 変数の優先順位を体感する。 terraform.tfvarsとは別の値を、コマンド実行時にterraform plan -var="任意の変数名=別の値"のように指定し、-varで渡した値がtfvarsファイルより優先されることを確認する。CI/CDや複数人開発で「どの値が実際に使われるか」を判断する上で必要な理解になる。
⚠️ つまずきやすいポイント
  • terraform.tfvarsには環境固有の値や、場合によっては秘密情報を含めるため、Gitでは絶対に管理しない（テナンシーOCID等のOCID自体はパスワードのような秘密情報ではないが、このファイルには秘密情報を含める可能性があるため、ファイル単位でGit管理対象から外す）。まだGitを導入していない状態だが（Git導入は来週）、来週.gitignoreを作ったら真っ先にこのファイルを登録すること。
✅ 成果物
🧭 到達判定
  • -varオプションで渡した値がtfvarsファイルより優先される、という変数の優先順位を説明できる
WEEK 04目安 4.5h

Subnet構築（Git管理開始）

🎯 このタスクのゴール
ここまでのコードをGitHubで管理できるようにする。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの変更」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/05-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業用フォルダに cd コマンドで移動してから、以降の操作を行う。
  2. Gitをインストールする（未導入の場合）。 PowerShellで
    winget install Git.Git
    を実行する。インストール後、新しいPowerShellでgit --versionが表示されることを確認する。
  3. Terraformコードは9月week4で作成済みのoci-learning-logリポジトリに置く（新規リポジトリは作らない）。ローカルにcloneしていない場合はgit cloneしてから作業する。
  4. .gitignoreに*.tfstate、*.tfstate.backup、terraform.tfvars、.terraform/を追加し、これまでgit initしていなければgit initしてから、ここまでのコードを一度git add→git commit→git pushでmainブランチにpushしておく（土台として1回だけ）。
  5. 作業用のbranchを切る。 これ以降の変更は、mainに直接コミットするのではなくbranch上で行う習慣をここから始める。
    git checkout -b feature/add-subnets
  6. このbranch上でoci_core_subnetリソースをPublic/Privateの2つ分コード化する。
  7. terraform fmtでコードを整形し、terraform validateで文法エラーが無いことを確認してから、terraform planで作成内容を確認し、terraform applyする。
  8. CLIでも確認する。 oci network subnet list --compartment-id <コンパートメントOCID>を実行し、コンソールとCLIの両方でSubnetが作成されていることを確認する。
  9. branch上でcommitし、pushする。
    git add . git commit -m "Add public/private subnets" git push -u origin feature/add-subnets
    mainブランチではなくfeature/add-subnetsbranchにpushされていることをGitHub上で確認する（このbranchのPull Request作成・レビュー・mainへのmergeは、1月以降にあらためて扱う）。
⚠️ つまずきやすいポイント
  • 初回のgit push時、ブラウザが自動で開いてGitHubへのログインを求められることがある（Git Credential Managerという仕組み）。エラーではないので、そのままブラウザ側でログイン・許可すればよい。
✅ 成果物

terraform.tfvars
🧭 到達判定
  • mainに直接コミットせず、branch上で変更を進める理由を説明できる
  • .gitignoreに含めるべきファイルと、その理由を説明できる
