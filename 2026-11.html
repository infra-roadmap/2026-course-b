11月：Terraform入門

コースB：OCI限定コース（AWS資格を目指さない）

ここからは手作業ではなく、コードでインフラを構築する「Terraform」を学びます。教材はOracle公式の日本語チュートリアルを使用します。

💼 この月で実務的にできるようになること：手作業で作っていたOCIリソースをTerraformコード（HCL）として書き起こし、init／plan／applyの流れとGitでのコード管理を、実務のIaC運用の基本として自分ひとりで回せるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
Terraformインフラをコードで作るツール「IaC（Infrastructure as Code）」の代表的なツールの1つ。手作業をコードに置き換える
HCLTerraformが使う専用の記述言語HashiCorp Configuration Languageの略。JSONに近いが、もう少し人間が書きやすい構文
ProviderTerraformが操作するクラウドの種類を指定する設定「OCIを操作します」という宣言をコードの先頭に書く
plan / apply変更内容の予告 / 実際の適用plan＝「これから何を作る/変えるか」の確認、apply＝実際に実行
state（ステート）Terraformが管理する「現在の状態」の記録実際に作られたリソースの情報がファイルに記録される。壊すと復旧が大変なので取り扱い注意

WEEK 01目安 4h

Terraform概要、環境構築、Provider

🎯 このタスクのゴール
手作業でポチポチ作っていたVCN等を、これから「コード」で再現できるようにするための土台を作り、Terraformから実際にOCIへ接続できることまで確認する。
📚 使う教材
  • Oracle公式チュートリアル（日本語）「Terraformの設定」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/01-summary.htm
🛠 具体的な手順
  1. 作業フォルダを作る。 PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。以降のTerraformのコードはすべて、ユーザーフォルダ直下のoci-learning-logフォルダに置く（9月に作ったGitHubのリポジトリと同じ名前にしておく）。
    New-Item -ItemType Directory -Force $env:USERPROFILE\oci-learning-log cd $env:USERPROFILE\oci-learning-log
    以降、PowerShellを開き直したら毎回、最初にこのcdを実行してから操作する（開き直した直後は別の場所にいる）。
  2. Terraformをインストールする。 PowerShellを「管理者として実行」で開き、
    winget install HashiCorp.Terraform
    を実行する（wingetはWindows標準のパッケージ管理ツール）。インストール後、新しいPowerShellを開き直してterraform -versionでバージョンが表示されることを確認する。本コースではTerraform v1.12.0以上を使用する（3月に使用するOCI Native Backendの要件のため）。表示されたバージョンがv1.12.0未満の場合は、HashiCorp公式サイトから最新版を再インストールする。
  3. OCI CLIをインストールする。 次のリンクからWindows用MSIインストーラー（v3.95.0）を直接ダウンロードする：oci-cli-3.95.0-Windows-Server-Installer.msi。ダウンロードした.msiファイルをダブルクリックして実行し、インストーラーの画面の指示に従って進める（設定はすべて初期値のままでよい）。インストール後、新しいPowerShellを開き直してoci --versionでバージョンが表示されることを確認する（開き直さないとPATHが反映されず、コマンドが見つからないと表示される）。
  4. APIキーを発行し、認証情報を設定する。 「準備→①→②→③」の順に進める。
    【準備】OCIDを2つ控える。 OCIコンソール右上のプロファイルアイコン→「自分のプロファイル」（旧表記は「ユーザー設定」）を開き、「詳細」タブの「OCID」の「コピー」でユーザーOCIDをメモ帳に貼って控える（ocid1.user.で始まる文字列）。テナンシーOCIDも、プロファイルメニュー内のテナンシー名の項目を開き、同様に控える（ocid1.tenancy.で始まる文字列。画面名が違って見つからない場合は「テナンシ」「OCID」で探す）。2つを取り違えないよう、メモ帳に「ユーザー：」「テナンシー：」と書き分けておく。
    ①ローカルで鍵ペアを作る。
    (1) 念のため、既存の設定ファイルの控えを取る。PowerShellでCopy-Item $env:USERPROFILE\.oci\config $env:USERPROFILE\.oci\config.bak -ErrorAction SilentlyContinueを実行する（設定ファイルが無い場合は何も起きない）。
    (2) oci setup configを実行する。最初に、手順の説明とドキュメントへのリンクが英語で表示されるが、質問ではないので読み飛ばす。
    (3) 続けて英語の質問が上から順に1つずつ表示されるので、次のように答える（貼り付けはPowerShell上で右クリック）。
    Enter a location for your config [C:\Users\<ユーザー名>\.oci\config]:
  → 何も入力せずEnter
Config file: C:\Users\<ユーザー名>\.oci\config already exists. Do you want add a profile here?
(If no, you will be prompted to overwrite the file) [Y/n]:
  → ※この質問は、設定ファイルがすでにある場合のみ表示される。n と入力してEnter
    （Enterだけだとデフォルトの Y になるので、必ず n を打つ）。続けて上書きの確認が出たら許可する
Enter a user OCID:
  → 準備で控えた ocid1.user. で始まる値を貼り付けてEnter
Enter a tenancy OCID:
  → 準備で控えた ocid1.tenancy. で始まる値を貼り付けてEnter
Enter a region by index or name(e.g. ...):
  → リージョンの一覧が表示される。コンソール右上に表示されている自分のリージョン
    （東京なら ap-tokyo-1）の番号または名前を入力してEnter
Do you want to generate a new API Signing RSA key pair? ... [Y/n]:
  → Y と入力してEnter
Enter a directory for your keys to be created [C:\Users\<ユーザー名>\.oci]:
  → 何も入力せずEnter
Enter a name for your key [oci_api_key]:
  → 何も入力せずEnter
Public key written to: C:\Users\<ユーザー名>\.oci\oci_api_key_public.pem
  → 質問ではなく、公開鍵を書き出したという表示。読み飛ばす
Enter a passphrase for your private key ("N/A" for no passphrase):
  → N/A と入力してEnter（Enterだけだと同じ質問が繰り返し表示される。
    パスフレーズを設定するとTerraform側で追加設定が必要になる）
    (質問の文言は、OCI CLIのバージョンで多少異なることがある。「[...]」の部分にはデフォルト値が表示される。もし Enter the name of the profile you would like to create: が表示された場合は、上の n ではなく Y と答えてしまっている。Ctrl+C で中断し、(2)からやり直す。)
    (4) 最後に、鍵ファイルや設定ファイルを書き出したことを示す英語のメッセージと、Fingerprintの行が表示されたら完了。dir $env:USERPROFILE\.ociを実行し、oci_api_key.pem（秘密鍵）、oci_api_key_public.pem（公開鍵）、config（設定ファイル）の3つがあることを確認する。Fingerprintの値は③の確認に使う（画面を閉じても、configファイルで後から確認できる）。秘密鍵は他人に渡さず、Gitにも入れない。
    ②公開鍵をOCIコンソールに登録する。 PowerShellでGet-Content $env:USERPROFILE\.oci\oci_api_key_public.pem | Set-Clipboardを実行して公開鍵の中身をコピーする。コンソールで「自分のプロファイル」を開き、「トークンおよびキー」タブの「APIキー」から「APIキーの追加」を押す。表示された画面で「公開キーの貼付け」を選んで貼り付け、「追加」を押す。
    ③登録できたか確認する。 追加すると「構成ファイルのプレビュー」が表示される。その中のfingerprintが、ローカルの$env:USERPROFILE\.oci\config（メモ帳で開く：notepad $env:USERPROFILE\.oci\config）のfingerprintと一致していればOK。
    この②を忘れると、①だけでは認証が通らない点に注意。
  5. CLIの疎通確認をする。 oci iam compartment list --compartment-id <テナンシーOCID>の<テナンシーOCID>を、準備で控えたテナンシーOCID（ocid1.tenancy.で始まる値。ocid1.user.ではない）に置き換えて実行し、認証設定が正しくできているかをOCI CLIから確認する（コンパートメント一覧がJSON形式で返ってくればOK）。エラーが出た場合は、下の「つまずきやすいポイント」を確認する。
  6. Providerを記述する。 手順1で作った作業フォルダ（oci-learning-log）にprovider.tfを作り、チュートリアルのサンプルをコピーして、次の5つの値を自分のものに書き換える。5つの値はいずれも$env:USERPROFILE\.oci\configに書かれており、右のコメントのとおり対応している（この書き方では、Terraformはconfigファイルを読まず、ここに書いた値でOCIに認証する。「どの値を渡して認証しているのか」を目に見える形にするため、今回はあえて明示的に書く）。
    provider "oci" {
  tenancy_ocid     = "ocid1.tenancy.oc1..xxxx"          # configの tenancy
  user_ocid        = "ocid1.user.oc1..xxxx"             # configの user
  fingerprint      = "xx:xx:xx:...:xx"                  # configの fingerprint
  private_key_path = "C:/Users/<ユーザー名>/.oci/oci_api_key.pem"  # configの key_file
  region           = "ap-tokyo-1"                       # configの region
}
    秘密鍵のパスをコードに書くときは、Windowsでも\ではなく/区切りで書く（例："C:/Users/<ユーザー名>/.oci/oci_api_key.pem"。\のままだとHCLの文字列としてエラーになる）。書くのは秘密鍵の「中身」ではなく「置き場所（パス）」なので、鍵そのものがコードに入るわけではない。なお、公式サンプルはこれらの値を変数（var.xxx）で渡す形になっている。ここでは仕組みを見えやすくするため直接書くが、Week 3のVariableで変数に切り出す際に、このprovider.tfの値も対象に含める（Gitに載せる前に済ませる）。書き換えたら、notepad provider.tfで開いて見直し、サンプルのxxxxや<ユーザー名>が1つも残っていないことを確認する（5つの値がすべて自分の値になっていること）。1つでも残っていると、次の疎通確認で認証エラー（401）になる。
  7. Terraformから接続できるか確認する（疎通確認）。 ここまでの確認はOCI CLIの確認であり、Terraformがつながるかどうかはまだ確かめていない。provider.tfと同じ作業フォルダ（oci-learning-log）にcheck.tfを作り（VS Codeまたはメモ帳で新規ファイルを作って保存する。メモ帳の場合は、保存時に「ファイルの種類」を「すべてのファイル」にしないとcheck.tf.txtになってしまう）、次の内容を書く（テナンシー内の可用性ドメイン名を読み取るだけで、リソースは何も作られない）。
    data "oci_identity_availability_domains" "ads" {
  compartment_id = "ocid1.tenancy.oc1..xxxx"   # テナンシーOCID
}

output "ads" {
  value = data.oci_identity_availability_domains.ads.availability_domains[*].name
}
    ここから先のコマンド（terraform initなど）は、すべてPowerShellに入力して実行する（手順1で開いたPowerShell、または開き直したPowerShell。VS Codeを使っている場合は内蔵のターミナルでもよい）。Terraformは、コマンドを実行したフォルダにある.tfファイルをすべて読み込むため、必ず作業フォルダの中で実行する。まずPowerShellで次を実行し、provider.tfとcheck.tfの2つが表示されることを確認する。
    cd $env:USERPROFILE\oci-learning-log dir *.tf
    表示されない場合は、別のフォルダにいるか、ファイルの保存場所が違っている。2つ表示されたら、そのまま同じPowerShellで次の順に実行する。
    terraform init terraform plan terraform apply
    initはProviderのダウンロード、planは実行内容の予告、applyは実際の実行。applyで確認を求められたらyesと入力する。最後にads = tolist([ "xxxx:AP-TOKYO-1-AD-1", ])のように可用性ドメイン名が表示されれば、Providerの設定は成功（tolist(...)が付くかどうかや改行の入り方は、Terraformのバージョンで多少変わるが、可用性ドメイン名が表示されていれば問題ない。0 addedと表示されるのも正常で、今回は読み取りだけでOCIには何も作っていないため。outputは「結果を画面に表示する」ブロック。詳しくはVariable・Outputの回で扱う）。確認できたらcheck.tfは削除してよい。
⚠️ つまずきやすいポイント
  • 作業フォルダ（oci-learning-log）は、この先もずっと使い続ける。フォルダを移動・削除したり、別の場所に作り直したりしない。applyすると、Terraformが「何を作ったか」を記録するterraform.tfstateがこのフォルダに作られる。.tfファイルだけを別フォルダへ移すと、Terraformは何も作っていない状態からやり直し、すでにあるVCNを重複して作ろうとする。
  • 「Terraform」と「OCI CLI」は別物。OCI CLI（oci setup config）は鍵と認証情報ファイル（~/.oci/config）を作るための道具で、Terraformは実行時にOCI CLIを呼び出さない。Terraformは、provider.tfに書いた値（configの内容を書き写したもの）でOCIに認証する、という関係を理解しておくと混乱しにくい（configを参照させる書き方は、3月のBackendで扱う）。
  • oci setup configで鍵を作っただけでは認証は通らない。生成された公開鍵をOCIコンソール側にも登録する、という2段階セットであることを忘れないこと。
  • oci setup configの途中で「config がすでに存在する（already exists）」という英語の質問が出ても、エラーではない。①の(3)のとおりnと答えて上書きする（(1)で控えを取ってあるので、元の内容はconfig.bakに残る）。
  • oci setup configで、パスフレーズの質問（Enter a passphrase for your private key）がEnterを押しても繰り返し表示される場合は、N/Aと入力する。
  • 疎通確認でNotAuthenticated（401）のようなエラーが出たら、②の登録漏れ、またはfingerprintの不一致を疑う。コンソールに表示された値とローカルのconfigの値を見比べる。
  • CLIの疎通確認は通るのに、Terraformだけエラーになる場合は、provider.tfに書き写した5つの値のどれかが誤っている可能性が高い。まず、サンプルのxxxxや<ユーザー名>を書き換え忘れていないか確認する（最も多い原因。tenancy_ocid・user_ocid・fingerprintにxxxxが残っていると401-NotAuthenticatedになる）。そのうえで、configの内容と1つずつ見比べる。「Invalid escape sequence」のようなエラーなら秘密鍵パスの\を/に、NotAuthenticated（401）系ならfingerprint・公開鍵の登録・ユーザーOCIDとテナンシーOCIDの取り違えを、鍵ファイルが見つからない系のエラーならprivate_key_pathのスペルとフォルダを確認する。
  • 鍵ファイルの権限に関する警告が出たら、oci setup repair-file-permissions --file $env:USERPROFILE\.oci\oci_api_key.pemを実行して権限を修正する。
  • OCIコンソールは表示言語を切り替えられる。本教材の項目名は日本語表示が前提。英語表示の場合は「My profile」→「Tokens and keys」タブ→「API keys」→「Add API key」→「Paste public key」に読み替える。

WEEK 02目安 4h

Resource基礎（VCN構築をコード化）

🎯 このタスクのゴール
10月に手動で作ったVCNと同じものを、コードから再現する。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの構築」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/03-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. main.tfにVCNを定義する。 provider.tfと同じ作業フォルダ（oci-learning-log）にmain.tfを新規作成する（Week 1でcheck.tfを作ったときと同じ要領。メモ帳の場合は、notepad main.tfと入力して開き、「新しいファイルを作成しますか？」で「はい」を選ぶとよい。VS Codeでもよい）。次の内容を書いて保存する。
    resource "oci_core_vcn" "main" {
  compartment_id = "ocid1.tenancy.oc1..xxxx"   # VCNを作る場所（コンパートメント）のOCID
  cidr_block     = "10.0.0.0/16"               # VCNのIPアドレス範囲
  display_name   = "tf-vcn"                    # コンソールに表示される名前
}
    1行目のresource "oci_core_vcn" "main"は「VCN（oci_core_vcnという種類のリソース）を、Terraformの中ではmainという名前で扱う」という宣言（resource "種類" "名前" { 設定 }の形）。"main"はコード内でこのVCNを指すための名前で、OCIコンソールに表示される名前ではない。コンソールに表示されるのはdisplay_nameの値。
    書き換える値は次の2つ。
    ・compartment_id：check.tfに書いたものと同じテナンシーOCID（ocid1.tenancy.で始まる値）を貼る。これは「テナンシー直下（ルートコンパートメント）にVCNを作る」という指定になる。10月の手動VCNをルート以外のコンパートメントに作っていて同じ場所に作りたい場合は、そのコンパートメントのOCID（ocid1.compartment.で始まる値）にする（コンソールの「アイデンティティとセキュリティ」→「コンパートメント」で確認できる）。
    ・cidr_block：10月に手動で作ったVCNと同じ値にする（OCIコンソールで10月のVCNの詳細画面を開くと確認できる。分からなければ10.0.0.0/16のままでもこの月の作業は進められる）。
    display_nameは、10月の手動VCNと見分けがつくようtf-vcnのような別の名前にしておく（コンソールにVCNが2つ並ぶため）。
    保存したら、PowerShellでdir *.tfを実行し、provider.tfとmain.tfが表示されることを確認する（main.tf.txtになっていたら、拡張子が.txtになっているので、名前を変更して.txtを外す）。xxxxが残っていると、後のplanでエラーになる。
  3. PowerShellで次を実行する（Week 1で実行済みだが、init／fmt／validateの役割の違いを意識して、あらためて実行する）。
    terraform init
  4. コードの整形と文法チェックを、次の順に実行する（plan/applyの前に必ず行う習慣にする）。
    terraform fmt terraform validate
    fmtはファイルを自動で整える（整形したファイル名が表示されることがあるが、何も表示されなくても正常）。validateはSuccess! The configuration is valid.と表示されれば合格。エラーが出た場合は、メッセージに書かれたファイル名・行番号の箇所を見直す。
  5. 次を実行し、「何が作られるか」の予告を確認する。
    terraform plan
  6. 次を実行し、確認を求められたらyesと入力して実際にVCNを作成する。
    terraform apply
  7. 10月に手動で作ったVCNは、この時点ではまだ削除しない。Public/Private Subnet・Route Table・NSG（public-nsg）・Compute（10月week3作成分）がまだ紐づいており、依存リソースを持つVCNはそのままでは削除できないため、これらを11月week4（Subnet）・12月（Compute）で順次Terraformコードとして移行し終えたあと、まとめて一本化する（9月分のVCN・Computeは10月着手前にすでに削除済みのため、この時点でのVCNは10月の手動VCNとここで作成したTerraform管理VCNの2個であり、上限内に収まっている）。
⚠️ つまずきやすいポイント
  • main.tfは、必ずprovider.tfと同じ作業フォルダ（oci-learning-log）に置く。別のフォルダに置くと、Terraformに読み込まれない。
  • サンプルのxxxxを書き換え忘れない。コード内のcompartment_idは、現時点では値を直接書いている（OCID自体はパスワードのような秘密情報ではない）。来週のWeek 3（Variable、Output）で、variables.tfに切り出す。
  • 値は半角の"（ダブルクォート）で囲む。全角の引用符や、{・}の閉じ忘れがあると、validateでエラーになる。
  • terraform applyはいきなり実行せず、必ずplanで内容を確認してから実行する癖をつける。
  • OCIのVCNは、内部にSubnetなどの依存リソースが残っている状態では削除できない。依存リソースを先に整理してから最後にVCN本体を削除する、という順序を意識しておく（実際に手動環境を片付けるのは、Subnet・Computeの移行が完了したあと）。
🧪 意図的な設定ミスからの復旧
HCLの文法ミスをわざと入れて、terraformのエラーメッセージを自分で読んで直せるようになる。
  1. 文法ミスを入れる。 notepad main.tfで開き、VCNブロックの最後にある閉じカッコ}の行を1つ削除して保存する（このほか、"を1つ消す、といった変更でもよい）。
  2. エラーを確認する。 terraform validateを実行し、表示されるエラーメッセージ（ファイル名・行番号・エラー内容）を読む。
  3. 直す。 エラーメッセージが指す箇所を自分で直し、terraform validateがエラー無しで通ることを確認する。
  4. 別のミスも試す。 手順3で直したmain.tfで、今度は属性名を意図的にtypoする（例：cidr_blockをcider_blockにして保存し、terraform validateを実行する）。確認できたら、必ずcidr_blockに戻してvalidateが通る状態にしておく（戻さないと次のplanが通らない）。「そのような属性は存在しない」系のエラーメッセージの読み方にも慣れておく。
✅ 成果物
🧭 到達判定
  • terraform validateのエラーメッセージを読んで、自分でコードを修正できる
  • 文法ミスと属性名のtypoで、エラーメッセージの出方が異なることを説明できる
WEEK 03目安 2.5h

Variable、Output

🎯 このタスクのゴール
CIDRやコンパートメントOCIDのような値を、コードの外に切り出して管理できるようにする。切り出したあともterraform planが「No changes」のままであることで、動作を変えずに整理できたことを確認する。
📚 使う教材
  • Oracle公式チュートリアル「変数の宣言」「出力値の照会」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/04-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. 切り出し前の基準を作る。 次を実行し、No changes. Your infrastructure matches the configuration.と表示されることを確認する。これは「Week 2で作ったVCNと、コードの内容が一致している」という意味で、この後の変数への切り出しが正しくできたかを判断する基準になる。
    terraform plan
    差分が出る場合は、Week 2のapplyが完了していない可能性があるので、先にWeek 2を終わらせる。あわせて、Week 1で作ったcheck.tfが残っていれば、値を直接書いた古いファイルなので削除しておく。
    Remove-Item check.tf -ErrorAction SilentlyContinue
    （ファイルが無い場合は何も表示されず、それで正常）
  3. 何を変数にするかを確認する。 今回、コードに直接書いてある次の8つの値を変数に切り出す（5つはprovider.tf、3つはmain.tfにある）。変数名は次のとおりに揃える（以降の手順でこの名前を使う）。
    変数名             いまの書き場所
tenancy_ocid       provider.tf の tenancy_ocid
user_ocid          provider.tf の user_ocid
fingerprint        provider.tf の fingerprint
private_key_path   provider.tf の private_key_path
region             provider.tf の region
compartment_id     main.tf の compartment_id
vcn_cidr_block     main.tf の cidr_block
vcn_display_name   main.tf の display_name
    仕組みは「variables.tf＝変数の宣言（名前と型だけ。値は書かない）」「terraform.tfvars＝実際の値（Terraformが自動で読み込む）」「.tfファイル＝var.変数名で値を呼び出す」の3点セット。
  4. variables.tfを作る（宣言）。 notepad variables.tfと入力して開き、「新しいファイルを作成しますか？」で「はい」を選ぶ（VS Codeでもよい）。次の内容を書いて保存する。
    variable "tenancy_ocid" {
  type        = string
  description = "Tenancy OCID"
}

variable "user_ocid" {
  type        = string
  description = "User OCID"
}

variable "fingerprint" {
  type        = string
  description = "API key fingerprint"
}

variable "private_key_path" {
  type        = string
  description = "Path to the API private key file"
}

variable "region" {
  type        = string
  description = "OCI region"
}

variable "compartment_id" {
  type        = string
  description = "Compartment OCID where the VCN is created"
}

variable "vcn_cidr_block" {
  type        = string
  description = "CIDR block of the VCN"
}

variable "vcn_display_name" {
  type        = string
  description = "Display name of the VCN"
}
    1つのvariable "名前" { ... }が変数1つの宣言。type = stringは「文字列の値を受け取る」という意味。default（初期値）は書いていないので、値はこの後のterraform.tfvarsなどから必ず渡す必要がある。（descriptionは説明文で、動作には影響しない。英語で書いているのは、メモ帳の保存形式による文字化けを避けるため）
  5. terraform.tfvarsを作る（実際の値）。 まず、現在の値を確認するため、notepad provider.tfとnotepad main.tfを開いておく（2つのウィンドウを並べると写しやすい）。そのうえでnotepad terraform.tfvarsを開いて新規作成し、現在provider.tf／main.tfに書いてある値と同じ値を次の形で書いて保存する。
    tenancy_ocid     = "ocid1.tenancy.oc1..xxxx"
user_ocid        = "ocid1.user.oc1..xxxx"
fingerprint      = "xx:xx:xx:...:xx"
private_key_path = "C:/Users/<ユーザー名>/.oci/oci_api_key.pem"
region           = "ap-tokyo-1"
compartment_id   = "ocid1.tenancy.oc1..xxxx"
vcn_cidr_block   = "10.0.0.0/16"
vcn_display_name = "tf-vcn"
    書き方は変数名 = "値"（値は半角の"で囲む）。xxxxや<ユーザー名>は例なので、必ず自分の実際の値に置き換える。値は手で打ち直さず、provider.tf／main.tfからコピーして貼り付ける（1文字違うだけで、後のplanで差分が出る）。ファイル名は必ずterraform.tfvarsにする（この名前だけ、Terraformが自動で読み込む）。保存後、dir terraform.tfvarsを実行して表示されることを確認する（terraform.tfvars.txtになっていたら、拡張子の.txtを外す）。
  6. provider.tfを変数に書き換える。 notepad provider.tfで開き、5つの値を次のようにvar.変数名に置き換えて保存する（値そのものはtfvarsに移したので、コードには書かない）。
    provider "oci" {
  tenancy_ocid     = var.tenancy_ocid
  user_ocid        = var.user_ocid
  fingerprint      = var.fingerprint
  private_key_path = var.private_key_path
  region           = var.region
}
    var.tenancy_ocidは「変数tenancy_ocidの値」を呼び出す書き方で、前後に"は付けない（付けると、var.tenancy_ocidという文字列そのものとして扱われる）。
  7. main.tfを変数に書き換える。 notepad main.tfで開き、VCNのブロックを次のように書き換えて保存する。
    resource "oci_core_vcn" "main" {
  compartment_id = var.compartment_id
  cidr_block     = var.vcn_cidr_block
  display_name   = var.vcn_display_name
}
    左側（compartment_idなど）はVCNリソースの属性名で変えない。右側だけをvar.変数名に変える。
  8. 切り出しが正しくできたか確認する。 次を順に実行する。
    terraform fmt terraform validate terraform plan
    validateがSuccess! The configuration is valid.になり、planが手順2と同じNo changes. Your infrastructure matches the configuration.になれば成功。「値の置き場所を変えただけで、中身は何も変わっていない」ことがplanで証明できる。
    ・-/+やmust be replaced、~の差分が出た場合：tfvarsの値が、最初にapplyしたときの値と違っている。applyせず（VCNが作り直されるおそれがある）、terraform state show oci_core_vcn.mainで実際の値を確認して、tfvarsを合わせ直す。
    ・Enter a value:と入力を求められた場合：tfvarsから値が渡っていない。Ctrl+Cで中断し、tfvarsのファイル名と、変数名のスペルが宣言と一致しているかを確認する。
  9. outputs.tfを作る（結果の出力）。 notepad outputs.tfで新規作成し、次を書いて保存する。
    output "vcn_id" {
  description = "OCID of the VCN"
  value       = oci_core_vcn.main.id
}
    oci_core_vcn.main.idは「oci_core_vcnのmainという名前のリソースの、id（OCID）」を指す（Week 2で付けた名前mainがここで使われる）。保存したらterraform fmt、terraform validateを実行し、terraform applyでyesと入力する。出力を追加しただけなので、Apply complete! Resources: 0 added, 0 changed, 0 destroyed.と、その下のOutputs:にvcn_id = "ocid1.vcn.oc1.ap-tokyo-1.xxxx"のように表示されれば成功（リソースは何も変わらない）。表示されたOCIDが、OCIコンソールのVCN詳細画面のOCIDと一致することも確認する。あとから値だけを見たいときはterraform output vcn_idで再表示できる。
  10. 変数の優先順位を体感する。 tfvarsは変更せず、コマンドで別の値を渡して、どちらが使われるかを確認する（PowerShellで次を実行）。
    terraform plan -var="vcn_display_name=tf-vcn-override"
    表示された差分の中で、display_name = "tf-vcn" -> "tf-vcn-override"のように、-varで渡した値に変わる予定になっていれば成功（Plan: 0 to add, 1 to change, 0 to destroy.）。tfvarsにはtf-vcnと書いてあるのに、-varの値が優先されたことが分かる。これは確認だけなので、applyはしない。確認後、terraform plan（-varなし）を実行し、No changes.に戻ることを確認する。優先順位は、弱い順に「default → 環境変数TF_VAR_名前 → terraform.tfvars → *.auto.tfvars → -var／-var-file」で、後に書いたものが勝つ。CI/CDや複数人開発で「どの値が実際に使われるか」を判断するときに必要な知識になる。
  11. 最後にファイルを確認する。 dir *.tf*を実行し、main.tf、provider.tf、variables.tf、outputs.tf、terraform.tfvarsの5つがあることを確認する（check.tfは無くてよい）。
⚠️ つまずきやすいポイント
  • terraform.tfvarsには環境固有の値や、場合によっては秘密情報を含めるため、Gitでは絶対に管理しない（テナンシーOCID等のOCID自体はパスワードのような秘密情報ではないが、このファイルには秘密情報を含める可能性があるため、ファイル単位でGit管理対象から外す）。まだGitを導入していない状態だが（Git導入は来週）、来週.gitignoreを作ったら真っ先にこのファイルを登録すること。
  • var.xxxには"を付けない。region = "var.region"と書くと、リージョン名が「var.region」という文字列になり、エラーになる。
  • Reference to undeclared input variableと出たら、var.名前の名前がvariables.tfの宣言と違っている（スペルミス）か、宣言を書き忘れている。
  • Warning: Value for undeclared variableと出たら、terraform.tfvarsにあってvariables.tfに宣言が無い変数がある。名前のスペルを揃える。
  • 切り出しのあとのplanで-/+（作り直し）や~（変更）が出たら、applyしない。cidr_blockのように、変更するとVCNが作り直しになる値がある。作り直しになると、Week 4で作るSubnetなど、VCNにぶら下がるリソースにも影響する。
  • terraform.tfvarsは、作業フォルダ直下に置く。別のフォルダやterraform.tfvars.txtだと読み込まれず、Enter a value:と入力を求められる。

  • 変数に切り出したあと、planが「No changes」になることで何が確認できるか説明できる

WEEK 04目安 4.5h

Subnet構築（Git管理開始）

🎯 このタスクのゴール
ここまでのコードをGitHubで管理できるようにする。
📚 使う教材
  • Oracle公式チュートリアル「インフラストラクチャの変更」 https://docs.oracle.com/ja-jp/iaas/developer-tutorials/tutorials/tf-provider/05-summary.htm
🛠 具体的な手順
  1. PowerShell（またはコマンドプロンプト）を開く（スタートメニューで「PowerShell」と検索して起動。普段VS Codeを使っているなら内蔵のターミナル機能でもよい）。作業フォルダ（cd $env:USERPROFILE\oci-learning-log）に移動してから、以降の操作を行う。
  2. Gitをインストールする（未導入の場合）。 PowerShellで
    winget install Git.Git
    を実行する。インストール後、新しいPowerShellでgit --versionが表示されることを確認する。
  3. 作業フォルダをGitHubのリポジトリにつなぐ。 Terraformコードは9月week4で作成済みのoci-learning-logリポジトリに置く（新規リポジトリは作らない）。ここまでコードを書いてきた作業フォルダ（oci-learning-log）の中で、次の3つを順に実行する。git cloneは使わない（別の場所にフォルダができ、terraform.tfstateが置き去りになるため）。
    git init -b main git remote add origin https://github.com/<GitHubユーザー名>/oci-learning-log.git git pull origin main --allow-unrelated-histories
    GitHub上にある9月作成のREADME.mdが作業フォルダに取り込まれる（すでに別の場所へcloneしてしまった場合は、作業フォルダの中身をすべてcloneしたフォルダへ移し、以降はそのフォルダを作業フォルダとして使う。terraform.tfstateも忘れずに移す）。
  4. 作業フォルダ直下に.gitignoreを新規作成し、*.tfstate、*.tfstate.backup、terraform.tfvars、.terraform/を書く。そのうえで、ここまでのコードをmainブランチに一度pushしておく（土台として1回だけ）。
    git add . git commit -m "Add VCN and base code" git push -u origin main
  5. 作業用のbranchを切る。 これ以降の変更は、mainに直接コミットするのではなくbranch上で行う習慣をここから始める。
    git checkout -b feature/add-subnets
  6. このbranch上でoci_core_subnetリソースをPublic/Privateの2つ分コード化する。
  7. terraform fmtでコードを整形し、terraform validateで文法エラーが無いことを確認してから、terraform planで作成内容を確認し、terraform applyする。
  8. CLIでも確認する。 oci network subnet list --compartment-id <コンパートメントOCID>を実行し、コンソールとCLIの両方でSubnetが作成されていることを確認する。
  9. branch上でcommitし、pushする。
    git add . git commit -m "Add public/private subnets" git push -u origin feature/add-subnets
    mainブランチではなくfeature/add-subnetsbranchにpushされていることをGitHub上で確認する（このbranchのPull Request作成・レビュー・mainへのmergeは、1月以降にあらためて扱う）。
⚠️ つまずきやすいポイント
  • git pullで「refusing to merge unrelated histories」と出たら、--allow-unrelated-historiesの付け忘れ。git pushが「rejected」になる場合は、先にgit pull origin main --allow-unrelated-historiesを実行していない可能性が高い。
  • 初回のgit push時、ブラウザが自動で開いてGitHubへのログインを求められることがある（Git Credential Managerという仕組み）。エラーではないので、そのままブラウザ側でログイン・許可すればよい。
