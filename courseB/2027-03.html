3月：Terraform実務設計

コースB：OCI限定コース（AWS資格を目指さない）

実務でよくあるTerraformの運用設計（Backend管理・秘密情報管理）を学び、最後に「事前準備・認証設定が完了していれば、Terraformの実行部分は最小コマンドで環境を再現できる」仕組みまで整えます。Remote Stateの管理には、OCIが公式に提供する「OCI Native Backend」（backend "oci"）を使います。以前は、OCI Object StorageをRemote State先として使う方法として、Amazon S3互換API経由のbackend "s3"も使われていましたが、この教材ではOCI Native Backend（backend "oci"）を採用します（backend "s3"という機能自体が非推奨というわけではなく、OCI Object StorageをこのS3互換方式でRemote State先として使う構成が、OCI公式ドキュメント上では現在非推奨（deprecated）とされているため、この教材では扱いません）。比較・補足知識としては後述します。

💼 この月で実務的にできるようになること：tfstateをOCI Native Backendでリモート管理し、そのアクセス制御まで含めて設計できるようになります。APIキーやパスワードなどの秘密情報をコードから分離しつつ、「環境変数にすればSecretは安全」という誤解に陥らず、Stateとの関係まで正しく説明できるようになります。あわせて、Issue作成からPull Request・レビュー・mainへのmergeまでを一連の流れとして経験し、チーム開発を想定したTerraform運用ができるようになります。

WEEK 01目安 4h

Backend設定（Remote State管理・準備編）

🎯 このタスクのゴール
tfstateをローカルではなくクラウド上で安全に管理できるようにする。あわせて、「Remote Stateにすること」と「Stateへのアクセス制御」はセットで考える必要があることも押さえる。tfstateにはリソースの設定値（場合によってはSecretを含む値）が保存されるため、リモート化しただけで安全になるわけではなく、そのバケットを誰が読み書きできるかというアクセス制御が重要になる。
先に方式を1つ確認：この後の手順でTerraformの設定にbackend "oci"と書きます。これはOCIが公式に提供する「OCI Native Backend」で、OCI Object Storageをそのままリモートの状態管理先として使う仕組みです。以前はOCI Object StorageをAmazon S3互換API経由で使うbackend "s3"が使われていましたが、長期間有効な認証キー（Customer Secret Keys）を発行・管理する必要があり、OCI Object StorageをこのS3互換方式でRemote State先として使う構成は、OCI公式ドキュメント上でも現在は非推奨（deprecated）とされています（backend "s3"という機能自体がTerraform上で非推奨というわけではありません）。backend "oci"はTerraform 1.12以降で使えます。認証方式は複数選べますが、今回の教材では既存のOCI認証設定（例：~/.oci/configのDEFAULTプロファイル）を利用する構成とするため、この構成に限っては新しい鍵の発行は不要です（Customer Secret Keysの発行も同様に不要）。
📚 使う教材
  • Terraform公式ドキュメント（Backend Type: oci） https://developer.hashicorp.com/terraform/language/backend/oci
  • OCI公式ドキュメント（Object StorageでのState管理・OCI Native Backend） https://docs.oracle.com/en-us/iaas/Content/dev/terraform/object-storage-state.htm
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. terraform versionでバージョンが1.12以上であることを確認する（未満の場合は先にTerraform本体をアップデートする）。
  3. OCI認証設定が利用できることを事前に確認する。 backend "oci"は~/.oci/configのDEFAULTプロファイルを利用する前提のため、先にこの認証設定が有効かを確認しておく。PowerShellで
    oci os ns get --profile DEFAULT
    を実行し、テナンシーのNamespace文字列がエラーなく返ってくることを確認する（OCI CLI未導入の場合は、9月に導入済みのはずなのでoci --versionで先に確認する）。ここでエラーになる場合は、~/.oci/configにDEFAULTプロファイルの記載があるか、鍵ファイルのパス（key_file）が正しいかを見直してから先に進む。
  4. OCIコンソールで、バックエンド用のバケット（例：terraform-state-bucket）をObject Storageに作成する。作成時に「バージョニング」を有効にしておくと、誤削除時にStateを復元しやすくなる。
  5. バケットへのアクセスを絞る。 このバケットに対するPolicyを見直し、「manage object-family」のような広い権限ではなく、Terraformを実行するユーザー（またはグループ）にだけ、このバケットへの読み書き権限を絞る。まず学習用として、対象バケットに限定したmanage objects（オブジェクトの読み書き・削除）とread buckets（バケット情報の参照）の2つを設定し（例：Allow group <グループ名> to manage objects in compartment <コンパートメント名> where target.bucket.name = 'terraform-state-bucket'／Allow group <グループ名> to read buckets in compartment <コンパートメント名> where target.bucket.name = 'terraform-state-bucket'）、backend "oci"が問題なく動作することを確認する。そのうえで、実際にどの操作（読み取り・書き込みなど）が使われているかを確認し、manage objectsには削除など読み書き以外の操作も含まれるため、可能な範囲でさらに必要最小限の権限へ絞り込むことを検討する。この2つの権限設定はあくまで学習用に動作確認しやすい構成であり、それ自体が「最小権限」というわけではない点に注意する。tfstateには接続情報等の値が含まれうるため、「リモートに置いた＝安全」ではなく、誰が読めるかを制御して初めて安全になる、という考え方をここで実践する。
  6. environments/dev・environments/prodそれぞれのroot module（2月WEEK04で分けた呼び出し側）に、backend "oci"ブロックを設定する。バケット名・Namespace（「Object Storage」の設定画面で確認できるテナンシー固有の文字列）・リージョンは、dev/prodで同じバケットを使ってよい。ただしオブジェクトのキー名（key）は、dev/prodで必ず異なる値にする（例：environments/devはkey = "envs/dev/terraform.tfstate"、environments/prodはkey = "envs/prod/terraform.tfstate"）。同じBucketを使っていてもkeyが異なればTerraformは別々のStateとして扱うため、「同じBucket＝同じState」ではないことをここで理解する。dev/prodで同じkeyを共有すると、片方の環境の操作がもう片方のStateを書き換えてしまう危険があるため、絶対に共有しない。認証は、今回の教材では既存のOCI認証設定（~/.oci/configのDEFAULTプロファイル）を利用する構成とするため、この構成では新たに鍵を発行する必要はない。backend "oci"ブロックには、実際にどのプロファイルを参照するかを明示するためconfig_file_profile = "DEFAULT"を指定する。
  7. dev/prodでStateが分離されていることを確認する。 ①environments/devのbackend "oci"ブロックのkeyを確認する。②environments/prodのbackend "oci"ブロックのkeyを確認する。③①と②のkeyが異なる値になっていることを確認する。④OCIコンソールのObject Storageでバケットの中身を開き、envs/dev/terraform.tfstate・envs/prod/terraform.tfstateという別々のオブジェクトパスとして保存される想定になっていることを確認する。⑤dev/prodが同一のStateを共有していないことを、自分の言葉で1〜2行にまとめる。
  8. ここまで設定できたら一旦保存しておく。実際にローカルのtfstateをリモートへ移行するterraform init -migrate-stateの実行と動作確認は、次週WEEK02の冒頭で、dev/prodそれぞれについて行う。
⚠️ つまずきやすいポイント
  • この週は他の週に比べて設定項目が多く、つまずきやすい。Namespaceやリージョン識別子の指定を間違えるケースが多いので、公式ドキュメントのサンプルの形式を1文字ずつ照合しながら進めるとよい。うまくいかない場合は無理に自力で解決せず、次週に持ち越してもよい。
  • ネット上の記事では、まだOCI Object StorageをS3互換API経由のbackend "s3"で使う手順が数多く紹介されているが、これはOCI公式ドキュメント上では非推奨の旧方式（backend "s3"という機能自体が非推奨というわけではなく、あくまでOCIでのこの使い方が対象）。このロードマップではbackend "oci"（OCI Native Backend）を使うため、検索して見つけた記事がどちらの方式かを見分けてから参考にすること。
  • Remote State用のObject Storage Bucketでは、Stateの復旧性を高めるためVersioningを有効化することを推奨。
✅ 成果物
🧭 到達判定
  • Remote Stateにすることと、Stateへのアクセス制御は別問題ではなく一続きであることを説明できる
  • backend "oci"（OCI Native Backend）が、なぜ現在推奨される方式か説明できる
  • dev/prodでTerraform Stateを分離し、両環境が同一Stateを共有していないことを確認・説明できる
WEEK 02目安 4h

Remote State移行の実行確認、これまでのbranchのPRマージ、最小権限の考え方

🎯 このタスクのゴール
前週準備したBackend設定を使ってState移行を完了させる。あわせて、1月・2月からmergeせずに残っている2つのbranch（feature/three-tier-design、feature/prod-environment）について、実際にPull Requestを作成してmainへmergeし、「変更してcommitして終わり」ではなく「PRを経てmainに取り込まれて完了」という一連の流れを体験する。
📚 使う教材
  • OCI公式ドキュメント（Policy Referenceのベストプラクティス） https://docs.oracle.com/ja-jp/iaas/Content/Identity/Reference/policyreference.htm
🛠 具体的な手順
  1. State移行の実行：前週environments/dev・environments/prodそれぞれに設定したbackend "oci"ブロック（keyはdev/prodで別々）の状態で、environments/dev・environments/prodそれぞれのディレクトリでterraform init -migrate-stateを実行し、ローカルのtfstateをリモートに移行する。移行後、それぞれでterraform planを実行して差分（diff）が出ないこと＝正しく移行できたことを確認する。
  2. Pull Requestベースのブランチ運用ルール（例：「1変更＝1branch＝1PR」「mergeしたbranchは削除する」等）を自分の中で定義し、READMEに書く。
  3. 1月のbranchをmergeする。 feature/three-tier-designをGitHub上でPushし、main向けのPull Requestを作成する。差分（3層構成のTerraformコード）を自分でひと通り読み返し、コメントを1つ以上つけてセルフレビューしてからmergeする。
  4. 2月のbranchをmergeする。 同様にfeature/prod-environmentのPull Requestを作成し、セルフレビュー後にmergeする。
  5. 「最小権限の原則」に沿ってこれまでのPolicyを見直し、広すぎる権限を絞る。
✅ 成果物
🧭 到達判定
  • terraform init -migrate-stateでState移行後、planで差分なしを確認できる
  • Pull Requestを作成し、セルフレビューを経てmainへmergeする一連の流れを実行できる
WEEK 03目安 4h

Secrets管理設計とPRフロー完全体験（Issue→branch→PR→merge）

🎯 このタスクのゴール
秘密情報の扱いを見直し、事故が起きない設計にする。あわせて、この変更を通じて「Issue作成→branch作成→Terraform変更→fmt→validate→plan→commit→Pull Request→レビュー→merge」という一連の流れを、今回初めて最初から最後まで通しで経験する（1月・2月はbranch作成〜commitまで、今週先頭のWEEK02では既存branchのmergeのみだった）。
先によくある誤解を正しておく：「環境変数（TF_VAR_xxx）にすればSecretは安全」というのは誤解。環境変数はコードにSecretをハードコードせず、Gitにも載せずに値を渡すための「入力方法の1つ」に過ぎない。Terraformは受け取った値をリソース作成に使うため、その値が結果的にtfstateへ保存されることがあり、tfstateを誰が読めるかというアクセス制御（WEEK01で設定したバケットへのアクセス制御）がセットで重要になる。またterraform.tfvarsもSecret専用ファイルではない。「Secretが入る可能性があるためGitで管理しない」という理解が正しい。
  • StateとSecretの関係を一直線で押さえる： ①Secretを環境変数やterraform.tfvars経由でTerraformに渡す →②Terraformがそれをリソース作成に使う →③結果としてその値がtfstateというファイル（WEEK01でOCI Native Backend上に置いたもの）に平文またはそれに近い形で書き込まれる場合がある（対象リソースの属性やProviderの実装によって、実際に保存されるかどうかは異なる） →④つまり「Secretを隠す」ことと「Stateを誰が読めるか」は別問題ではなく一続きの話であり、Gitからの隠蔽（.gitignore・環境変数化）とState自体へのアクセス制御（WEEK01のバケット権限）の両方が揃って初めてSecretが守られる、という順序で理解しておく。⑤変数にsensitive = trueを指定した場合も、これはterraform plan／apply実行時のコンソール出力やログ上で値を隠すためのものであり、tfstateファイルへの書き込み自体を防ぐものではない点に注意する（sensitive指定済みの値であっても、対象リソースの属性やProviderの実装によってはtfstateに平文で保存され得る）。
📚 使う教材
  • Terraform公式ドキュメント https://developer.hashicorp.com/terraform/docs
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. Issueを作成する。 GitHub上で「Secretの環境変数化とアクセス制御の見直し」といったタイトルのIssueを立て、やること（.gitignore見直し／Secretの環境変数化／確認方法）を簡単に書く。
  3. branchを作成する。
    git checkout -b fix/secrets-handling
  4. .gitignoreの見直しをする（terraform.tfvarsや*.tfstate系がすべて除外対象になっているか確認する）。
  5. APIキー等のSecretは、Terraformの入力変数（variable "xxx" {}）として宣言し、その値を環境変数（TF_VAR_xxx）経由で渡す形に切り替える。TF_VAR_xxxはあくまで自分で定義したTerraformの入力変数に値を渡すための仕組みであり、OCI Provider自体の認証情報（WEEK01で設定した~/.oci/configのDEFAULTプロファイル）を置き換える汎用的な環境変数ではない点に注意する。ハードコードとGitコミットを避けるための方法であり、これだけで「安全になる」わけではない、という前提で進める。
  6. terraform fmtで整形し、terraform validateを実行して、環境変数経由に変更した後もコードにエラーが無いことを確認する。
  7. 実際に切り替わったことを確認する。 terraform.tfvarsから該当の値を一時的にコメントアウトし、環境変数だけの状態でterraform planが問題なく通ることを確認する（通らなければ環境変数名の設定ミスなので、その場で直す）。
  8. これまでの設計を棚卸しし、セキュリティ設計チェックリストを作成する。study-notesリポジトリに2027-03-security-checklist.mdとして保存し、pushする。
  9. commit・push・PR作成する。
    git add . git commit -m "Move secrets to environment variables and review .gitignore" git push -u origin fix/secrets-handling
    手順2で作ったIssueへのリンクをPRの説明に貼り、変更内容（何を・なぜ変えたか）を書く。
  10. セルフレビューしてmergeする。 PRの差分を自分で読み返し、Secretがコード上に残っていないか・.gitignoreが正しいかをコメントで指摘・確認したうえでmainへmergeする。
✅ 成果物
💡 サンプルを見る

セキュリティ設計チェックリストの例（study-notesリポジトリの2027-03-security-checklist.mdとして箇条書きで保存するイメージ）：

  • ☑ terraform.tfvarsがGit管理対象に含まれていないか
  • ☑ ポリシーに「manage all-resources」のような広すぎる権限が残っていないか
  • ☑ APIキー・パスワードがコード内にハードコードされていないか
  • ☑ tfstateがリモートバックエンド（Object Storage等）で管理され、かつバケットへのアクセスが絞られているか
  • ☑ SSH等の管理ポートが0.0.0.0/0に開放されたままになっていないか
🧭 到達判定
  • 「環境変数にすればSecretは安全」という誤解を、Stateとアクセス制御の関係を含めて訂正できる
  • Issue→branch→PR→mergeの一連の流れを最初から最後まで自分で実行できる

「最小コマンドで環境再現」の仕組み構築

🎯 このタスクのゴール
誰か（未来の自分も含む）が見ても、迷わず環境を再現できる状態にする。この週はCourse B（OCI限定コース）の最終評価課題と位置付け、「OCIアカウント・認証情報・Region・必要なOCID等の事前準備と認証設定が完了していれば、READMEに従ってTerraformを実行するだけで環境を再現できる」というゴールに加えて、READMEなどのドキュメントを見れば第三者が（事前準備を済ませた上で）環境を再現できる状態になっているかを、下記の到達条件で確認します。
📚 使う教材
  • これまでのTerraformコード一式 https://github.com/
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. READMEに「事前準備（OCIアカウント・認証情報・Region設定・Backend用Bucket・必要なOCID等）」と「Terraform実行手順」を分けて記載する。事前準備さえ完了していれば、git clone→terraform init→terraform applyという最小コマンドで環境を再現できる状態を目指す（事前準備そのものを1コマンドにする必要はない）。
  3. 変数のデフォルト値や、サンプルterraform.tfvars.exampleを用意し、事前準備で埋めるべき値がREADME上で分かるようにする。
✅ 成果物
🏁 Course B 最終評価課題：到達条件

「事前準備後は最小コマンドで環境再現」というこの週のゴールを、Course B全体の最終評価として次の観点で確認します。

  • Terraformコードから環境を再現できる
  • Remote Stateを適切に利用できている
  • Moduleを利用している
  • Gitのbranch／PR／mergeの流れを実施できている
  • READMEだけで第三者が再現手順を理解できる
