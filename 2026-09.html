9月：OCI基礎

コースB：OCI限定コース（AWS資格を目指さない）

コースA（AWS資格コース）・コースB（OCI限定コース）ともに9月の内容はほぼ共通です。差分がある第4週のみ、コースBの内容を掲載しています。

💼 この月で実務的にできるようになること：OCIのアカウント作成からIAM（ユーザー・グループ・ポリシー）でのアクセス制御、コンパートメントによるリソース整理、Always Free枠でのLinuxサーバー構築・SSH接続までを、実際の画面操作で一通り自分の手で行えるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
OCIOracle Cloud InfrastructureOracleが提供するクラウドサービス。AWSやAzureと同じ「クラウドプロバイダー」の1つ
テナンシー自分専用の契約単位AWSでいう「AWSアカウント」に近いもの。OCIアカウントを作ると1つ払い出される
コンパートメントリソースを整理する「フォルダ」AWSにはこの概念がなく、OCI特有。「開発用」「本番用」のようにリソースをグループ分けする
IAMアイデンティティ・アクセス管理「誰が」「何に対して」「何をしていいか」を管理する仕組み。ユーザー・グループ・ポリシーの3つがセット
ポリシー権限のルール「グループAはコンパートメントBに対してこれができる」という許可を書いた文章。英語の文章に近い書き方をする
VCN自分専用の仮想ネットワークAWSでいう「VPC」と同じ役割。この中にサーバーなどを置いていく
Computeサーバー（仮想マシン）AWSでいう「EC2インスタンス」と同じ役割
Always Free永久無料枠一定のスペック内であれば期限なく無料で使えるOCIのリソース枠
SSH鍵安全にログインするための鍵「公開鍵」をサーバー側に登録し「秘密鍵」を自分のPCに持っておくことで、パスワードなしで安全にログインできる仕組み
OCPUOCIでのCPU数の単位1 OCPU ≒ CPUコア1つ分と考えてOK

WEEK 01目安 3h

OCIアカウント作成、全体像の把握

🎯 このタスクのゴール
OCIに無料でログインできる状態を作り、あとで必要になる情報をメモしておく。
📚 使う教材
  • Qiita「OCI ハンズオン 事前準備手順書」（suzukiyukizi） https://qiita.com/suzukiyukizi/items/e2f654a18b3ea872b575 ― 画面のスクリーンショット付きで登録の流れがそのまま書いてあります
  • OCI公式ドキュメント（日本語） https://docs.oracle.com/ja-jp/iaas/Content/home.htm
  • GitHub（無料アカウント） https://github.com/
🛠 具体的な手順
  1. Oracleアカウントを作成する。 https://www.oracle.com/jp/cloud/free/ にアクセスし「無料で始める」から登録。クレジットカード情報の入力を求められるが、これは本人確認のためで勝手に課金されることはない。Home Region（変更不可）の選択画面が出るので、日本から使うならJapan East (Tokyo)を選ぶ。
  2. メール認証をする。 届いた確認メールのリンクをクリック。数分〜数十分届かないこともある（迷惑メールフォルダも確認）。
  3. OCIコンソールにログインできることを確認する。 https://cloud.oracle.com/ にアクセスし、テナンシー名・ユーザー名・パスワードでログイン。画面上部にメニューバーが表示されればOK。
  4. あとで使う情報をメモしておく。 画面右上アイコン→「ユーザー設定」から、テナンシー名／ユーザーOCID／Home Regionを控える。11月のTerraform学習で必ず使う。これらはGitにコミットせず、ローカルのメモ帳かパスワードマネージャーに保存する（テナンシー名やOCIDはパスワードではないが、リポジトリに残す情報として習慣化しない方が安全）。
  5. 学習メモ用のリポジトリを作る（未作成の場合）。 https://github.com/ でGitHubアカウントを作成し、study-notesという名前でPrivateリポジトリを1つ作成する。これ以降、各週の「成果物」欄に出てくるメモ・対比表・チェックリストなどはMarkdownファイルとしてこのリポジトリに集約していく（機密情報は入れない）。9月第4週で作るoci-learning-logリポジトリ（Terraformコードや構成図を置く場所）とは別物として運用する。
⚠️ つまずきやすいポイント
  • クレジットカードの入力で不安になる人が多いが、Always Free対象として明示されたリソースを、Always Freeの上限内で利用する限り、通常の利用料金は発生しない。
  • OCIには「30日間の無料トライアル（$300クレジット）」と「Always Free」の2つの無料枠が重なって存在する。アカウント作成直後の30日間は、Always Free対象外のリソースも$300のクレジット内であれば無料で使える状態になっている。トライアル終了後（またはクレジットを使い切った後）も、アカウント自体はそのまま継続して利用でき、Always Free対象のリソースは引き続き無料で使い続けられる。一方、トライアルのクレジットで動かしていたAlways Free対象外の有料リソースは回収（停止・削除）の対象となるため、Always Free枠を超えるリソースはトライアル終了後は継続利用できない。トライアル終了前に、構成をAlways Free枠の範囲内に整理しておく必要がある。このロードマップでは常にAlways Free対象のシェイプ・サービスだけを使うよう指示しているため、30日間が過ぎても操作方法は変わらないが、「あれ、最初は動いていたのに」と感じる変化があれば、大抵はこのトライアル終了が原因。
  • Home Regionは一度決めると変更できない。「日本から使うなら東京」で問題ない。
✅ 成果物
🧭 到達判定
  • OCIコンソールにログインし、テナンシー名・ユーザーOCID・Home Regionを自分で確認できる
  • Always Free対象として明示されたリソースを、Always Freeの上限内で利用する限り、通常の利用料金が発生しない理由を説明できる
WEEK 02目安 3.5h

IAM（ユーザー/グループ/ポリシー）、Compartments

🎯 このタスクのゴール
「開発用の作業スペース（コンパートメント）」を作り、そこに対してだけ操作できるユーザーグループを作る。
📚 使う教材
  • OCI公式ドキュメント（Identity and Access Managementのページ） https://docs.oracle.com/ja-jp/iaas/Content/Identity/home.htm
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. コンパートメントを作る。「Identity & Security（アイデンティティとセキュリティ）」→「Compartments（コンパートメント）」→「Create Compartment（コンパートメントの作成）」。名前はdev。
  3. IAMグループを作る。「Domains（ドメイン）」→「Groups（グループ）」→「Create Group（グループの作成）」でdevelopersという名前のグループを作成する。
  4. ポリシーで権限を付与する。「Policies（ポリシー）」で対象コンパートメントをdevに切り替え、次の1文を入力する。
    Allow group developers to manage all-resources in compartment dev
    （※これは学習用に権限の設定方法を体験するための簡易ポリシーであり、実務では対象サービス・操作を絞った最小権限のポリシーを設計する。）
  5. テストユーザーで権限を確認する。「Domains（ドメイン）」→「Users（ユーザー）」→「Create User（ユーザーの作成）」でテスト用ユーザーを作成し、作成したdevelopersグループに追加する。そのテストユーザーでログインし直し（または別ブラウザ／シークレットウィンドウでログインし）、devコンパートメント内のリソースを操作できることを確認する（例：Computeインスタンスの一覧が見える、作成画面まで進める等）。ポリシーが正しく効いているかを、実際のユーザー権限で確かめる工程になる。
  6. AWSとの対比メモを作る。 User=IAM User、Group=IAM Group、Policy=IAM Policy、Compartment=（AWSに該当なし）、という対応を表でまとめる。study-notesリポジトリに2026-09-iam-comparison.mdとして保存し、pushする。
  7. OCI CLIでも同じ内容を確認する。 コンソール（ブラウザ）だけでなく、コマンドラインからも状態を確認できるようにしておく。PowerShellで
    winget install OracleCorporation.OracleCloudInfrastructure-CLI
    を実行してOCI CLIをインストールし、新しいPowerShellでoci --versionが表示されることを確認する。続けてoci session authenticateを実行するとブラウザが開きOCIへのログインを求められるので、ログインして認証を許可する（この方法はAPIキー登録が不要な簡易認証で、11月にTerraformから使う本格的なAPIキー認証とは別物）。認証後、oci iam compartment list --compartment-id <テナンシーOCID>を実行し、9月第1週でメモしたテナンシーOCIDを使って、コンソールで作成したdevコンパートメントがJSON形式の一覧に含まれていることを確認する。「コンソールで見えているものは、コマンドラインからも同じように見える」という感覚をここで持っておくと、11月以降のTerraform学習がスムーズになる。
⚠️ つまずきやすいポイント
  • OCIのポリシー文は英文に近い書き方。「Allow（グループ）to（できること）in（どこで）」の順番だけ覚えれば読み書きできる。
  • 「Groups（グループ）」の場所はコンソールのアップデートで変わることがある。見当たらない場合は検索窓で「Group」を検索する。
✅ 成果物
💡 サンプルを見る

IAM対比メモの例です（study-notesリポジトリの2026-09-iam-comparison.mdにそのままコピーして自分用に書き換えてOK）：

OCIAWS役割
UserIAM User個人のログインアカウント
GroupIAM Groupユーザーの集まり
PolicyIAM Policy権限のルール
Compartment（該当なし）リソースを整理する箱
🧭 到達判定
  • User／Group／Policy／Compartmentの役割の違いを自分の言葉で説明できる
  • OCIのポリシー文（Allow ... to ... in ...）の構造を読める
WEEK 03目安 5〜6h

VCN概要、Compute基礎（Always Freeインスタンス起動）

🎯 このタスクのゴール
自分専用の仮想ネットワークを作り、その中に無料のサーバーを1台立てて実際にログインする。
📚 使う教材
  • OCI公式ドキュメント（Networking（ネットワーキング）／Compute（コンピュート）のページ） https://docs.oracle.com/ja-jp/iaas/Content/Network/Concepts/overview.htm
  • Zenn「Oracle Cloud (OCI) でインスタンス作成からVCN設定・OSのポート解放まで」 https://zenn.dev/wyuma/articles/5fce8ef5042303
🛠 具体的な手順
  1. （準備）ブラウザで https://cloud.oracle.com/ を開き、9月第1週で作成したテナンシー名・ユーザー名・パスワードでログインしておく（すでにログイン済みならこの手順は不要）。以降の「〇〇を開く」はログイン後の画面からの操作を指す。
  2. VCNを作る。「Networking（ネットワーキング）」→「Virtual Cloud Networks（仮想クラウド・ネットワーク）」→「Start VCN Wizard（VCNウィザードの開始）」でデフォルト構成を作成する。
  3. Always Free対象のサーバーを1台起動する。「Compute（コンピュート）」→「Instances（インスタンス）」→「Create Instance（インスタンスの作成）」を開く。イメージは初期状態でOracle Linuxになっていることが多いため、「Change Image」からUbuntuを選び直す。Shapeも初期状態はAlways Free対象外のことが多いため、「Change Shape」→「Ampere」タブ→VM.Standard.A1.Flex（2 OCPU・12GB程度）に必ず変更する（変更し忘れると課金対象のShapeのまま作成されてしまう）。
  4. SSH鍵を発行し、その場でダウンロードする。「Generate a key pair for me」を選ぶと秘密鍵・公開鍵が生成される。この画面を閉じると秘密鍵は二度と取得できないため、「Save Private Key」ボタンで必ずその場でPCに保存する。
  5. ここからは自分のPCで操作する。 ここまではブラウザ（OCIコンソール）での操作だったが、ここからは自分のPCの「PowerShell」を使う。スタートメニューで「PowerShell」と検索して起動し、鍵ファイルが入っているダウンロードフォルダに移動する。
    cd ~\Downloads
  6. 鍵ファイルの権限を絞る。 ダウンロード直後の状態だとエラーになることがあるため、自分だけが読める状態に変更しておく。
    icacls .\ダウンロードした鍵ファイル.key /inheritance:r icacls .\ダウンロードした鍵ファイル.key /grant:r "$($env:USERNAME):(R)"
  7. SSHで接続する。
    ssh -i .\ダウンロードした鍵ファイル.key ubuntu@サーバーのIPアドレス
    初回接続時は Are you sure you want to continue connecting (yes/no/[fingerprint])? と聞かれるので yes と入力してEnterを押す。
  8. スペックを確認する。htopでCPU・メモリを確認する（なければsudo apt update && sudo apt install htop）。
⚠️ つまずきやすいポイント
  • 「Permission denied」の多くは鍵ファイルの権限設定忘れか、ユーザー名の誤り（Ubuntuならubuntu）が原因。
  • sshコマンドが「認識されていません」と出る場合、Windowsの設定で「OpenSSHクライアント」が無効になっている可能性がある。設定→アプリ→オプション機能→「OpenSSH クライアント」を追加すると使えるようになる。
  • Shapeの変更を忘れてAlways Free対象外のまま作成してしまうと課金が発生する。作成後に気づいた場合は、一度インスタンスを削除して作り直すのが安全。
  • Always Freeの上限（Ampere A1は2026年6月の仕様変更後、合計2 OCPU・12GB）を超えると課金対象になるので注意。この上限はCompute（Ampere A1）だけの話ではなく、Block Volume（合計200GB）・Object Storage（20GB）・Outbound Data Transfer（月10TB）など、Always Free対象のリソース種別ごとにテナンシー全体で共有される上限がそれぞれ存在する。複数のプロジェクトやコンパートメントを跨いで使っていても、この上限はアカウント（テナンシー）全体で合算されるため、「このコンパートメントではまだ余裕があるはず」という考え方はできない点に注意する。
  • 「Out of host capacity」等のエラーで作成に失敗することがある。 これはAmpere A1（無料枠）の人気が高く、リージョン内の在庫が一時的に無くなっている状態で、自分の設定ミスではない。対処法：①時間を置いて（数分〜半日後）同じ手順でリトライする、②Availability Domain（AD-1/AD-2/AD-3など）が選べる場合は別のADを試す、③どうしても作成できない場合は一旦AMDベースのVM.Standard.E2.1.Microで代用し、後日Ampereが空いたタイミングで作り直す。焦って何度も連打する必要はない。
🧪 トラブルシュート演習：SSH接続が壊れた原因を特定する
正常につながっていたSSH接続を意図的に壊し、LinuxコマンドとOCI側の設定確認の両方を使って原因を切り分け、自力で復旧する。
  1. 復旧用の接続を確保しておく。 今つながっているSSH接続はそのままにして、別のPowerShellウィンドウ（またはタブ）をもう1つ開き、そちらでも同じ手順でComputeへSSH接続しておく。以降の作業はこの2つ目の接続を使う。
  2. 障害を起こす（次のどちらか1つを選ぶ）。 ①Compute（コンピュート）のVNICにアタッチされているNSGを開き、TCP 22番のIngressルールを一時的に削除する。②サーバー側（1つ目の接続）で
    sudo systemctl stop ssh
    を実行し、SSHサービス自体を止める。どちらを選んだかをメモしておく。
  3. 症状を確認する。 2つ目のPowerShellから改めてssh -i ...で接続を試み、失敗することを確認する（1つ目の接続はまだ生きているため、以降の調査に使える）。
  4. Linuxコマンドで切り分ける。 生きている1つ目の接続から、以下を順番に実行して結果を確認する。
    systemctl status ssh ss -lntp journalctl -u ssh -n 50
    systemctl status sshでサービスの状態、ss -lntpで22番ポートがLISTENしているか、journalctl -u ssh -n 50で直近のログにエラーが出ていないかを確認する。②を選んだ場合はここで停止に気づけるはずで、①の場合はこの時点ではOS側は正常に見える。
  5. OS側で異常が見えない場合はOCI側を疑う。 ①を選んだ場合、OCIコンソールでNSGのIngressルールを開き、22番が本当に削除されているかを確認する。「OS側は正常＝クラウド側の設定を疑う」という切り分けの考え方をここで体感する。
  6. 原因を特定し、復旧する。 ①の場合はNSGのIngressルールを元に戻す。②の場合はsudo systemctl start sshでサービスを再開する。復旧後、2つ目の接続から再度SSH接続できることを確認する。
  7. 確認した順番を記録する。「①何を確認したか→②何が分かったか→③次に何を確認したか→④原因→⑤復旧方法」の順で、3〜5行程度の箇条書きメモを作る。study-notesリポジトリに2026-09-ssh-troubleshoot.mdとして保存し、pushする。
✅ 成果物
🧭 到達判定
  • systemctl status／ss -lntp／journalctlを使い、SSH接続不可の原因をOS側から切り分けられる
  • OS側が正常に見える場合はクラウド側（NSG等）の設定を疑う、という切り分けの考え方を説明できる
