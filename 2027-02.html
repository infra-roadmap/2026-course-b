2月：Terraform総合演習②

コースB：OCI限定コース（AWS資格を目指さない）

コードをモジュール化し、再利用性・保守性の高い構成に整理します。Moduleは単なるファイル分割ではなく、「同じコードを複数の環境・複数の用途で使い回すための仕組み」として理解し、実際にdev環境とprod環境で同じModuleを使い分けるところまで体験します。

💼 この月で実務的にできるようになること：重複の多いTerraformコードをモジュール（module）として部品化し、環境ごとに使い回せる保守性の高いディレクトリ構成に整理できるようになります。さらに、CIDRなどの環境差分をvariableで吸収しながら、同じModuleをdev／prodの複数環境に対して適用できるようになります。

📖 この月で出てくる用語

用語ひとことで言うともう少し詳しく
Module（モジュール）コードの再利用可能な部品VCN構築用、Compute（コンピュート）構築用のようにコードをまとめて、使い回せるようにする仕組み。単なるファイル分割ではなく、複数の環境・複数の用途で再利用するための設計
environments（環境ディレクトリ）同じModuleを呼び出す側を、環境ごとに分離したディレクトリenvironments/dev、environments/prodのように分け、それぞれが同じModuleを異なる変数値で呼び出す

週次タスク

WEEK 01目安 3.5h

Module化の考え方（＝複数環境で再利用するための設計）

🎯 このタスクのゴール
同じコードを何度も書かずに済むよう、部品化の考え方を理解する。ここで大事なのは「ファイルを分けること」自体ではなく、「同じModuleを、CIDRやインスタンス数などの値だけ変えて、dev環境・prod環境のように複数の環境で使い回せるようにすること」だと理解すること。
📚 使う教材
  • Terraform公式ドキュメント（Modules） https://developer.hashicorp.com/terraform/language/modules
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. Moduleの概念（入力変数・出力・呼び出し方）をドキュメントで学習する。
  3. 今月のゴールとなる最終ディレクトリ構成を先に確認しておく。 以下のように、modules/配下に部品を置き、environments/devとenvironments/prodという呼び出し側を分けて、同じModuleを異なる変数値（CIDR等）で2つの環境に適用する、という今月のゴール像をイメージしてからWEEK02以降に進む。
    modules/ network/ security/ compute/ environments/ dev/ prod/
    なお、このディレクトリ構成はTerraformの唯一の正解ではなく、今回の学習で採用する構成の一例。目的はModule化の考え方・環境分離・再利用・変数による差分管理を身につけることであり、ディレクトリ構成そのものを暗記することではない。
✅ 成果物
🧭 到達判定
  • Moduleが「ファイル分割」ではなく「複数環境で再利用するための仕組み」である理由を説明できる
WEEK 02目安 3.5h

networkモジュール化

🎯 このタスクのゴール
ネットワーク関連のコードを1つの部品にまとめる。ただし単にファイルを移すだけでなく、CIDRなど環境によって変わる値をModule内にハードコードせず、呼び出す側から渡せるようにvariables.tfを設計する。
📚 使う教材
  • Terraform公式ドキュメント https://developer.hashicorp.com/terraform/docs
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. modules/networkディレクトリを作成し、VCN/Subnet/Route Table（ルート表）をモジュール化する（NSGはセキュリティに関わるリソースのため、WEEK03で作るmodules/security側にまとめる。network moduleではネットワークの土台となるVCN・Subnet・Route Tableのみを扱う）。variables.tfにvcn_cidr・public_subnet_cidrなどを定義し、これまでコード中に直接書いていたCIDR値を変数参照に置き換える。
  3. 取得すべき値（VCNのOCIDやSubnetのOCIDなど）をoutputs.tfに定義し、あとでsecurity moduleやcompute moduleから参照できるようにする。
  4. ルートのmain.tfからmodule "network" { source = "./modules/network" vcn_cidr = "10.0.0.0/16" ... }のように、変数を渡す形で呼び出す。
  5. これまでroot直下で管理していたVCN/Subnet/Route Tableをmoduleへ移すと、Terraform state上のリソースアドレスが変わる（例：oci_core_vcn.this → module.network.oci_core_vcn.this）ため、movedブロック等でstate上のアドレス変更を引き継ぐ。
  6. terraform fmt -recursiveでmodules配下も含めて整形し、terraform validateで文法チェックする。あわせてterraform planを実行し、意図しないリソースの削除・再作成が発生していないことを確認する。
✅ 成果物
🧭 到達判定
  • CIDR等の環境差分をハードコードせず、variableとして呼び出し側から渡せるModuleを書ける
  • network moduleがVCN・Subnet・Route Tableというネットワーク基盤を担当し、NSGはsecurity module側の責務であることを説明できる
WEEK 03目安 3.5h

security/computeモジュール化

🎯 このタスクのゴール
同様の考え方で、セキュリティ関連・Compute（コンピュート）関連もモジュール化する。network moduleと同様、環境によって変わりうる値（許可CIDR、Shape、インスタンス数など）はハードコードせず変数化する。
📚 使う教材
  • Terraform公式ドキュメント https://developer.hashicorp.com/terraform/docs
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. modules/security（NSG/Policy）、modules/compute（Instance）を切り出す。modules/computeにはinstance_shapeやinstance_countを変数として持たせ、呼び出す環境によって台数やShapeを変えられるようにする。
  3. network moduleのoutputs.tfで出力したSubnetのOCIDなどを、module "security"・module "compute"の入力として受け渡す（subnet_id = module.network.private_app_subnet_idのような形）。
  4. 既存のNSG/Policy/Instanceリソースをmodules/security・modules/computeへ移す場合も、リソースアドレスが変わるためmovedブロック等でstate上のアドレス変更を引き継ぐ。
  5. terraform validateを実行し、モジュール分割後もコードにエラーが無いことを確認する。あわせてterraform planで不要な削除・再作成が発生していないことを確認する。
✅ 成果物
🧭 到達判定
  • network moduleのoutputsを、security/compute moduleの入力として受け渡せる
WEEK 04目安 5h

ディレクトリ整理とdev/prod再利用実践

🎯 このタスクのゴール
誰が見ても分かりやすいフォルダ構成に整えたうえで、「同じModuleを複数環境で使い回す」ことを実際に体験する。dev環境に加えてprod環境を新設し、CIDRなどの差分をvariableで吸収しながら、同じmodules配下のコードをそのまま2つの環境に適用する。Module変更はbranch上で管理する。
📚 使う教材
  • GitHub上の公開Terraformリポジトリ（検索して構成を参考にする） https://github.com/search?q=oci+terraform+language%3AHCL&type=repositories
🛠 具体的な手順
  1. PowerShellを開き、作業用フォルダに cd で移動してから、以降の操作を行う。
  2. 作業用のbranchを切る。 今週のModule変更・環境追加はbranch上で行う。
    git checkout -b feature/prod-environment
  3. environments/devのようにモジュール呼び出し側を分離し、これまでの構成をdev環境として位置づける（vcn_cidr = "10.0.0.0/16"など、WEEK02〜03で定義した変数に値を渡す）。
  4. environments/prodを新設する。 environments/prod/main.tfを作り、environments/devと同じmodules/network・modules/security・modules/computeを呼び出す。Module自体のコードは変更せず、vcn_cidr = "10.1.0.0/16"のようにCIDRだけをdevと重複しない値に変えて渡す。
  5. cd environments/prodでterraform init・terraform planを実行し、devと同じModuleコードのまま、prod用のリソース（別CIDRのVCN等）が計画されることを確認する。
  6. Always Free枠を使い切らないよう確認後は片付ける。 ネットワーク部分（VCN/Subnet）とセキュリティ部分（NSG）はapplyしたままでよいが、Compute部分はAmpere A1・E2.1.MicroのAlways Free枠に上限があるため、dev/prod分を同時に立てっぱなしにしない。片付けは、environments/prod/main.tfからmodule "compute"の呼び出しをコメントアウト（または削除）し、terraform planでCompute部分だけが削除対象になっていることを確認したうえでterraform applyする、という通常のコード変更＋plan/applyの流れで行う。
  7. CLIで全体像を確認する。 oci network vcn list --compartment-id <コンパートメントOCID>を実行し、dev用・prod用の2つのVCNが存在することをCLIから俯瞰できることを確認する。
  8. oci-learning-logリポジトリのREADME.mdに、dev/prod両方を含めたディレクトリ構成図と、各モジュールの役割（network＝VCN/Subnet/Route Tableを管理等）を1行ずつ追記する。
  9. branch上でcommitし、pushする。
    git add . git commit -m "Add prod environment reusing existing modules" git push -u origin feature/prod-environment
    このbranchのPull Request作成・レビュー・mainへのmergeは、3月にあらためて一連の流れとして扱う。また、ここで分けたdev/prod環境は、3月にそれぞれ独立したTerraform Remote State（tfstateのkeyをdev/prodで分離したもの）を持たせる設計につなげる。
⚠️ つまずきやすいポイント
  • 12月にも触れた通り、-targetは依存関係を無視するオプションではなく、指定したリソースを中心とした部分的な操作を行うためのオプション。対象範囲を絞る分、コードの依存関係と実際の状態がずれやすい。障害対応・復旧作業など限定的な場面で使う高度なオプションという位置づけであり、今回のようなCompute部分の通常の後片付けは、コード変更＋plan／apply（必要に応じて通常のterraform destroy）で行うのが基本、と覚えておく。
✅ 成果物
💡 サンプルを見る

モジュール化＋dev/prod再利用後のディレクトリ構成の例（oci-learning-logリポジトリの中身）：

oci-learning-log/
├── environments/
│   ├── dev/
│   │   └── main.tf        (vcn_cidr = "10.0.0.0/16" 等で呼び出す)
│   └── prod/
│       └── main.tf        (vcn_cidr = "10.1.0.0/16" 等、値だけ変えて同じmoduleを呼び出す)
└── modules/
    ├── network/
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    ├── security/
    │   ├── main.tf
    │   ├── variables.tf
    │   └── outputs.tf
    └── compute/
        ├── main.tf
        ├── variables.tf
        └── outputs.tf
🧭 到達判定
  • 同じModuleコードを変更せず、変数の値だけを変えてdev/prod2つの環境に適用できる
  • -targetオプションが通常運用で常用するものではなく、障害対応など限定的な場面で使う高度なオプションであることを説明できる
